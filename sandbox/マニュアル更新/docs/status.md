### 主な発見・判断

1. **指定管理者はLGWAN接続不可** → インターネット接続系に配置。LGWAN-ASP登録は必須要件ではない
2. **横浜市自身がRAG実証済み**（選挙管理事務、精度9割）→ 庁内に理解者がいる可能性
3. **横浜市はGoogle提携あり、ただしメインはMS** → NotebookLMが近日解禁見込み、PoCに最適
4. **NotebookLMはログが取れない** → PoCは「体感・合意形成」に割り切り、本番は別製品
5. **既製品SaaSが本命**（OfficeBot, PKSHA等）→ 更新運用をサービスが吸収してくれる

### 提案書の致命的な穴（次回対応）

1. **定量データがない** — 電話件数・事務所数・対象規模が不明
2. **免責と実効性の矛盾** — 「参考情報」なら結局電話に戻る問題
3. **運用体制が空白** — 育てる人間の工数・TCOが未定義
4. **トーンの問題** — 「独自解釈」が現場を否定する表現
5. **代替案との比較がない** — AIなしの選択肢を並べていない
6. **本件マニュアルでのPoC未実施** — 他ドメインの精度を根拠にしている

### Whyドキュメントから判明したこと

- **本当の課題**: ツール不足ではなく「マニュアルが現場と切り離された構造そのもの」
- **相談者の危機感**: 表面化していない誤対応が相当数あるのではないか（推測段階）
- **双方の被害者構造**: 事務所も「後から対応が違うと言われるリスク」を抱えている
- **まだ足りない情報**: きっかけ、具体エピソード、この提案の行き先（誰に見せるか）

### 提案書の位置づけ（判明）

- 相談者が**係長・課長に持っていくための叩き台**
- 相談者が実情に即して調整する前提 → コスト・規模感は相談者が入れる
- 我々が提供すべきは**構造の言語化**と**反論への備え**
