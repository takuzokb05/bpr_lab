# 「育てるマニュアル」構想

## マニュアル運用の構造転換 — AIを活用した双方向フィードバック基盤

---

## 1. 課題認識

### 制度運用の構造的な問題

共用部分代行管理制度では、指定管理者事務所が住民からの問い合わせ対応を含む多くの実務を担っています。日常的な問い合わせ件数は相当数にのぼりますが、そのすべてが市へ確認されているわけではありません。

現在、市が作成するマニュアルは**一方向型の運用**になっています。

- 市が作成し、年1回程度で改訂し、事務所に送付する
- 事務所側からのフィードバック回路がない
- マニュアルの記載が抽象的な部分や、現場の実情に即していない表現があっても、改善につながりにくい

### 現場で起きていること

事務所の職員は、住民が目の前で困っている状況で対応しなければなりません。

- 一つ一つ市に確認するのは手間がかかる
- 電話での問い合わせは時間的・心理的ハードルが高い
- 結果として、事務所の経験と善意に基づいて判断するケースが多い

こうした現場判断の中に、マニュアルの記載が分かりにくいために**市の考えと異なる対応**になってしまうケースが含まれています。表面化していないだけで、本来とは違う回答をしているケースは少なくないと考えられます。

### 双方にとっての不利益

この構造は、市と事務所の双方に不利益をもたらしています。

| | 不利益 |
|---|--------|
| **事務所** | 判断に迷いながら対応せざるを得ない。後から「対応が違う」と言われるリスクを常に抱えている |
| **市** | 制度が意図した形で運用されているか把握できない。問題が起きてからの事後対応になりがち |

**事務所が困っているのは、経験や努力が足りないからではなく、確認しやすい手段と、マニュアルが現場の声を反映する仕組みがないから**です。

### 問題の構造

```
市がマニュアルを作る → 事務所が受け取る → 現場で判断する → ズレが蓄積する
        ↑                                                      │
        └──── 現場の声が届く仕組みがない ←────────────────────┘
```

これは**マニュアルの出来不出来の問題ではなく、マニュアルが現場と切り離されている構造そのものの問題**です。

---

## 2. 解決の方向性

### 目指す姿: マニュアルを「配るもの」から「育てるもの」へ

マニュアルと現場の間に**双方向の回路**を作り、日常の業務の中でマニュアルが自然に改善されていく仕組みを構築します。

```
事務所                    AI                      市
  │                       │                       │
  ├─ 質問する ──────────→│                       │
  │                       ├─ マニュアルに基づき回答 │
  │                       │                       │
  │    （AIで判断できない） │                       │
  │                       ├─ 市に確認を依頼 ─────→│
  │                       │                       ├─ 回答を返す
  │                       │← 回答をマニュアルに反映 ┤（市が承認）
  │                       │                       │
  │                       │   ┌ 質問ログを集約 ┐  │
  │                       │   │ どこで迷う？    │→│← 改善の根拠に
  │                       │   │ 何が足りない？  │  │
  │                       │   └────────────────┘  │
```

### この仕組みで変わること

| 現状 | 導入後 |
|------|--------|
| 事務所が迷っても確認しにくい | 24時間、気軽にマニュアルを確認できる |
| どこで困っているか市が見えない | 質問ログから「迷いやすいポイント」が可視化される |
| マニュアル改善の根拠がない | 質問の蓄積がそのまま改善の材料になる |
| 年1回の更新 | 日常のやり取りを通じて継続的にアップデート |
| 事業者が変わると知見がリセット | 知識がシステムに蓄積され、引き継がれる |

### AIを使う理由

この課題には「メールやチャットで問い合わせ窓口を増やす」「マニュアルを書き直す」といった対策も考えられます。しかし、それだけでは以下の点が解決しません。

| 代替策 | 限界 |
|--------|------|
| メール・チャット窓口の新設 | 市側の対応負荷が増える。回答にタイムラグが出る |
| マニュアルの全面改訂 | 現時点での改善はできるが、改訂後にまた現場との乖離が始まる |
| 定期研修・勉強会 | 全事務所に均一に実施するのが難しい。人が変わればリセットされる |

AIを使うことで、**市の対応負荷を大きく増やさずに**、事務所が即座に回答を得られ、かつ質問ログが自然に蓄積されてマニュアル改善の根拠になる——という循環が実現します。

## 3. 実現の見通し

### 横浜市での実績

横浜市は2024〜2025年にかけて、選挙管理事務においてRAG（検索拡張生成）技術を用いた生成AI実証を行い、**約4,500ページの法令・マニュアルに基づくQ&Aで回答精度 約9割**を達成しています（NTT東日本 伴走支援）。

共用部分代行管理のマニュアルでも同様のアプローチが有効と考えられますが、精度は**実際にマニュアルを投入してテストしてみないと断言できません**。そのため、まずは小規模なテストで回答精度を確認するステップを設けます。

### 全国の動向

- 千代田区: 庁内マニュアルをAIに投入し、年間22,700時間の効率化を見込む
- 埼玉県庁: 25,000人の職員向けAI Q&Aで電話問い合わせを大幅削減
- 総務省: 庁内事務のQ&Aに生成AI活用を推奨（ガイドブック第4版）
- 都道府県の87%、指定都市の90%が生成AIを導入済み（2025年6月末時点）

### ネットワーク上の位置づけ

指定管理者はLGWAN（自治体閉域網）に接続していないため、本システムはインターネット接続系に配置します。個人情報はAIに入力しない設計とし、セキュリティ対策（多要素認証・通信暗号化・監査ログ等）を実施します。

## 4. 進め方

### 基本方針

- 技術導入の前に**現場の実態把握**を優先する
- 全事務所への一斉導入はしない。**前向きな事務所から小さく始める**
- 事務所が蓄積してきた現場の知見を否定するのではなく、**その知見を公式に取り込む仕組み**にする

### Phase 0: 現場を知る

| やること | 内容 | 成果物 |
|---------|------|--------|
| 質問パターンの棚卸し | 事務所が受ける質問・判断パターンを洗い出す | 質問パターン一覧 |
| マニュアルの棚卸し | よく参照される部分、迷いやすい部分を特定 | 改善候補リスト |
| 事務所の実情把握 | 事務所訪問により、業務の流れと困りごとを直接把握 | 現場調査レポート |

事務所が独自に作っている「補足メモ」「申し送り」は、マニュアルと現場のギャップそのものです。これを拾い上げることが、AIに何を教えるべきかを決める最重要の情報になります。

### Phase 1: 小さく試す

| やること | 内容 | 成果物 |
|---------|------|--------|
| 回答精度テスト | 実際のマニュアルをAIに投入し、代表的な質問で精度を確認 | テスト結果レポート |
| 体感デモ | 関係者にAI Q&Aを体験してもらう | 合意形成 |
| 協力事務所の確保 | 前向きな1〜2事務所でパイロット運用 | パイロット体制 |

**回答精度テスト**は、他部署の実績をそのまま根拠にせず、**このマニュアルで本当に使えるかを自分たちの目で確認する**ためのステップです。

### Phase 2: 循環を回す

| やること | 内容 | 成果物 |
|---------|------|--------|
| 本番システム導入 | 製品を選定し、パイロット事務所で運用開始 | 稼働システム |
| 確認依頼フローの確立 | AIで判断できない質問を市に確認する仕組み | 運用ルール |
| ログ分析 | 質問傾向からマニュアルの改善点を抽出 | 改善提案レポート |

```
AIで判断できない質問の流れ:

  事務所が質問 → AIが回答
      │
      ├─ 回答で解決 → 完了
      │
      └─ 判断できない/不十分
            ↓
         市に確認依頼 → 市が回答
            ↓
         市が回答を確認・承認 → マニュアル（知識ベース）に反映
            ↓
         次回から同じ質問にAIが回答可能に
```

マニュアル（知識ベース）の更新は**市の承認を経てから反映**します。AIが勝手にルールを変えることはありません。

### Phase 3: 展開・定着

- パイロットの成果をもとに他事務所へ段階的に展開
- 事業者交代時の知識ベース引継ぎ手順を整備
- 年次レビューで回答精度の総点検と満足度調査を実施

### 全体の流れ

```
    Phase 0          Phase 1          Phase 2          Phase 3
  現場を知る       小さく試す       循環を回す      展開・定着
  ┌────────┐     ┌────────┐     ┌────────┐     ┌────────┐
  │質問棚卸し│     │精度テスト│     │本番導入 │     │他事務所 │
  │マニュアル│ →  │体感デモ │ →  │確認依頼 │ →  │事業者交代│
  │事務所訪問│     │協力事務所│     │ログ分析 │     │年次改善 │
  └────────┘     └────────┘     └────────┘     └────────┘
```

## 5. 期待される効果

### 事務所にとって

- 電話せずにマニュアルの内容を確認できる手段が増える
- 「後から対応が違うと言われる」リスクが減る
- 困りごとが市に伝わり、マニュアルの改善に反映される

### 市にとって

- 現場でどこに迷いがあるかがデータで把握できるようになる
- 問題が顕在化する前に兆候を検知できる
- マニュアル改善の根拠が自然に蓄積される

### 制度全体として

- 事務所間の対応品質のばらつきが小さくなる
- 事業者が交代しても知識がシステムに残り、引継ぎのロスが減る
- 「市が作る→事務所が従う」から「双方の知見で育てる」関係への転換

## 6. AIの回答をどう位置づけるか

### 基本的な考え方

AIの回答は**マニュアルの記載内容に基づく参考情報**です。定型的な手続き確認（申請書の書き方、提出先など）ではそのまま活用でき、判断が分かれるケースでは市への確認を促す設計とします。

### 回答の段階分け（案）

| 段階 | 説明 | 事務所の対応 |
|------|------|------------|
| **明確に回答できる** | マニュアルに明記されている事項 | そのまま参考にして対応 |
| **関連する記載はあるが判断が必要** | 類似の記載はあるが完全一致しない | AIの回答を参考にしつつ、必要に応じて市に確認 |
| **回答できない** | マニュアルに該当する記載がない | 市に確認依頼（AIが自動で案内） |

「AIが答えたから正しい」でも「AIは信用できないから使わない」でもなく、**回答の確度に応じて使い分ける運用ルール**を事務所と市の間で合意しておくことが重要です。

## 7. 事務所との関係づくりについて

この仕組みは、事務所の業務を**監視するためのもの**ではありません。

### 大切にしたいこと

- 事務所が長年蓄積してきた**現場対応の経験と知見を尊重**する
- その知見をマニュアルに取り込む**橋渡しの仕組み**として活用する
- 質問ログは**制度改善のための分析に使い、事務所の評価には使わない**

<!-- ※ 質問ログの非評価利用は、協定書・仕様書レベルで明記することを推奨 -->

### 協力事務所への配慮

パイロット期間中、協力事務所には通常業務に加えてフィードバック等の負担が生じます。市側からのサポート体制（問い合わせ窓口の明確化、定期的なフォロー等）を用意し、一方的な負担にならないよう配慮します。

## 8. 技術的な選択肢

Phase 1の中で比較検討し、本制度に最適な方式を選定します。

| 方向性 | 概要 | 特徴 |
|--------|------|------|
| **A. 自治体向け既製品** | 自治体での導入実績がある製品を利用 | 運用が容易。更新はファイル差替えで可能 |
| **B. クラウドAI基盤** | Azure OpenAI等をベースに構築 | カスタマイズの自由度が高い |
| **C. 既存チャットツール連携** | LINE WORKS等と連携 | 現場が馴染みやすいUI |

選定にあたっては以下を重視します。

- マニュアル更新時に**技術者なしで知識ベースを更新できる**か
- 指定管理者（市の外部組織）がインターネット経由でアクセスできるか
- 指定管理者が交代してもシステムと知識が引き継がれるか
- AIで判断できない質問を市に自然に確認依頼できるか

## 付録: 想定される質問と回答

### Q. AIでなくても、メールやチャットで窓口を増やせばいいのでは？

窓口を増やすだけでは、市側の対応負荷が増える一方です。AIを挟むことで、マニュアルに書いてある内容は即座に回答でき、市には本当に判断が必要なケースだけが上がってくるようになります。また、質問ログが自然に蓄積されることで、マニュアルのどこを改善すべきかが見えるようになるのは、窓口の新設だけでは実現しません。

### Q. マニュアルを書き直すのが先ではないか？

マニュアルの改善は並行して取り組むべきテーマです。しかし、一度改訂しても時間が経てば再び現場との乖離が始まります。日常の質問をデータとして蓄積し、**継続的に改善し続ける仕組み**がなければ、同じ問題が繰り返されます。

### Q. AIの回答が間違っていたら誰が責任を取るのか？

AIの回答はマニュアルに基づく参考情報であり、最終的な判断の責任は制度の設計者である市にあります。だからこそ、AIが判断できないケースを市に確認する**エスカレーションの仕組み**を組み込みます。また、回答精度はPhase 1のテストで事前に確認し、実用に耐えるレベルかどうかを判断した上で導入を進めます。

### Q. 事務所にとっては仕事が増えるだけではないか？

この仕組みの主な目的は、事務所が「迷ったときにすぐ確認できる」環境を作ることです。電話で確認する手間が減り、後から「対応が違う」と指摘されるリスクも減ります。事務所が蓄積してきた現場の知見をマニュアルに取り込む橋渡しにもなります。追加の作業を強いるのではなく、**日常業務の中で自然に使える仕組み**を目指します。

### Q. 事業者が変わったらどうなるのか？

質問と回答の蓄積はシステム側に残るため、事業者が変わっても知識は引き継がれます。新しい事業者のスタッフも、過去の質問事例を参照しながら業務を立ち上げることができます。知識が人ではなくシステムに蓄積される設計です。
