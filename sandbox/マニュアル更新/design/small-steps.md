# スモールステップ設計 — 指定管理者に寄り添う導入アプローチ

## 前提: なぜ「寄り添い」が必要か

指定管理者は構造的に微妙な立場にいる：

- **市の指示には従う義務がある**が、日常運用は自分たちが回している自負がある
- **「AIで監視される」と感じたら抵抗される** — Q&Aログ＝監視ツールと捉えられるリスク
- **事業者が3〜5年で交代する** → 「自分たちのために改善する」モチベーションが湧きにくい
- **ITリテラシーに大きな差**がある — 事務所によって年齢構成・経験がバラバラ
- **「また市から新しいこと言われた」疲れ** — 制度変更や新システム導入への慣れと疲弊

→ **技術導入の前に、まず「一緒に良くする」関係を作る必要がある**

---

## Phase 0: 現場を知る（1〜2ヶ月）

### 目的
AIの話をする前に、現場の実態を把握し、事務所との信頼関係を作る。

### Step 0-1: QAの棚卸し

**やること**: 事務所が日常的に受ける質問・判断のパターンを洗い出す

```
収集方法（負担が小さい順）:
① 事務所に「最近困った質問」を5つ書いてもらう（紙1枚のアンケート）
② 市への電話問い合わせ記録を1ヶ月分集計する
③ 可能なら、事務所に1日同行して業務を観察する
```

**整理の観点**:

| 分類 | 例 | 対応 |
|------|-----|------|
| **マニュアルに書いてある** | 「退去時の手続きは？」 | → AIで即答可能 |
| **マニュアルに書いてあるが解釈が分かれる** | 「この場合は修繕対象？」 | → AIで回答 + 根拠提示 |
| **マニュアルに書いてない** | 前例のないケース | → 市へエスカレーション |
| **個人情報を含む判断** | 「この住民の滞納状況は？」 | → AIの対象外（明確に除外） |

**成果物**: 質問パターン一覧表（50〜100件）+ 分類

### Step 0-2: マニュアルの棚卸し

**やること**: 現行マニュアルの構造と「使われ方」を把握する

```
確認すること:
- マニュアルは何ページ・何章あるか
- よく参照される章とほぼ読まれない章はどこか
- 最後に更新されたのはいつか
- 事務所独自の「補足メモ」「付箋」「申し送り」が存在するか ← 重要！
```

**なぜ「補足メモ」が重要か**:
事務所が独自に作っている非公式な手順書・メモこそが、
マニュアルと現場の**ギャップそのもの**。これを拾わないとAIに何を教えるべきかがわからない。

### Step 0-3: 事務所との関係づくり

**やること**: 「一緒に良くしたい」というメッセージを伝える

```
NGアプローチ:
× 「AIを入れて業務を効率化します」 → 「仕事を奪われる」と感じる
× 「Q&Aログで問題点を可視化します」 → 「監視される」と感じる
× 「マニュアルが自動更新されます」 → 「勝手にルールが変わる」と感じる

OKアプローチ:
○ 「電話しなくてもすぐ答えがわかる仕組みを一緒に考えたい」
○ 「事務所の皆さんが普段困っていることを教えてほしい」
○ 「皆さんの経験や工夫をマニュアルに反映したい」
```

## Phase 1: 小さく試す（2〜3ヶ月）

### Step 1-1: NotebookLMで「体感」してもらう

**やること**: NotebookLMにマニュアル1〜2章分のPDFを投入してデモ

**なぜNotebookLMか**:
- 横浜市はGoogleと提携済み → 新規サービス導入の承認プロセスを回避できる
- 市の担当者が自分でPDFを投入して質問するだけ → 技術者不要
- 現時点では未解禁だが、近い将来使えるようになる見込み

**NotebookLMの限界（割り切る）**:
- Q&Aログが取れない → フィードバック循環の検証は本番ツールで
- 指定管理者に提供する手段がない → あくまで市の内部検証用
- PoCの目的は「体感→合意形成」であり、本番ツールは別途選定

```
デモの見せ方:
- 市の担当者の目の前で、実際の質問を入力して見せる
- 「すごい」ではなく「あ、これ便利かも」と思わせるレベルを狙う
- 間違った回答が出たらチャンス → 「だからこそ現場の知見が必要なんです」
- 担当者自身に触ってもらう → 「自分でもできる」実感が重要
```

**対象の選び方**:
- Step 0-1の棚卸しで「マニュアルに書いてあるのに問い合わせが多い」領域を選ぶ
- 最も効果が見えやすく、かつ個人情報に触れないテーマ

### Step 1-2: 協力事務所を1〜2箇所見つける

**やること**: 全事務所一斉展開ではなく、前向きな事務所から始める

```
選定基準:
- ITに抵抗がないスタッフがいる
- 市との関係が良好
- 質問量がそこそこ多い（効果が見えやすい）
```

**協力事務所の役割**:
- 日常業務でプロトタイプを試用する
- 「使ってみてどうか」のフィードバックをくれる
- 他の事務所への口コミ元になる ← これが一番大事

### Step 1-3: 質問ログの蓄積開始

**やること**: プロトタイプの利用ログを収集し始める

```
この時点で見るべきこと:
- どんな質問が来るか（Step 0-1の想定と合っているか）
- AIが答えられなかった質問は何か → マニュアルの穴
- 同じ質問が複数事務所から来るか → 共通の困りごと
```

## Phase 2: フィードバック循環を回す（3〜6ヶ月）

### Step 2-1: 「AIが答えられなかった質問」の運用フロー

```
事務所がAIに質問
  ↓
AIが回答 → OK → 完了
  ↓ 回答できない/不十分
事務所が「わからなかった」ボタンを押す
  ↓
市の担当者に通知が飛ぶ
  ↓
市が回答を返す（メール or チャット）
  ↓
市の回答を知識ベースに追加（市が承認）
  ↓
次回から同じ質問にAIが答えられる
```

**ポイント**:
- 「わからなかった」を押すことにネガティブな印象を持たせない
- 「質問すること＝マニュアルを育てること」という文化を作る
- **市の承認なしに知識ベースは更新されない**（権限分離の原則）

### Step 2-2: マニュアル更新提案レポート

```
月次 or 四半期で:
- 「この部分への質問が多い」→ 記述がわかりにくい可能性
- 「この質問はマニュアルにない」→ 追記候補
- 「事務所ごとに解釈が違う質問」→ 記述の明確化が必要
```

**これが当初の構想にある「AIを介した対話の循環」の具体形**

### Step 2-3: 展開拡大

```
協力事務所での成果を報告
  ↓
他の事務所に「使ってみませんか」と声かけ
  ↓
事務所同士の口コミで広がるのが理想
  ↓
全事務所展開はPhase 2の成果を見てから判断
```

---

## Phase 3: 本格運用（6ヶ月〜）

### Step 3-1: 本番システム選定・調達
- Phase 1-2の知見をもとに製品選定（RFP作成）
- PoC成果を根拠に予算要求

### Step 3-2: 事業者交代への備え
- 知識ベースの引き継ぎ手順を仕様に含める
- 新事業者への研修プログラム（「AIの使い方」ではなく「AIと一緒に働く文化」）

### Step 3-3: 年次レビュー
- マニュアル全体の改訂タイミングでAIの回答精度を総点検
- 事務所からの満足度調査

## やってはいけないこと

1. **全事務所に一斉導入** — 抵抗勢力を一気に敵に回す
2. **「監視」を匂わせる** — Q&Aログは改善のため、評価のためではない
3. **技術の話から入る** — 事務所には「便利になる」体験から入る
4. **マニュアルの自動更新を約束する** — 市の承認プロセスは絶対に省略しない
5. **完璧を求めてから始める** — 精度70%でも「電話するより早い」なら価値がある
6. **事務所の非公式ノウハウを否定する** — むしろ「それを公式に取り込みたい」と伝える
