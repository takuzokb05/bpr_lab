# 技術選択肢 — 評価と整理

## 重要な前提: LGWAN制約の再整理

**指定管理者はLGWANに接続できない**（LGWANは自治体間の閉域網）。
したがって、指定管理者向けサービスは**インターネット接続系**に配置するのが標準。

```
三層分離における位置づけ:
  マイナンバー系   → 指定管理者アクセス不可
  LGWAN接続系     → 指定管理者アクセス不可
  インターネット系 → ★ここに配置する★
```

**つまり**: LGWAN-ASP登録は必須要件ではない。ISMAP登録が望ましい（総務省ガイドライン）が、
未登録でもCISOの責任で利用可能。ただし多要素認証・IP制限・監査ログ等は必要。

この前提により、当初「LGWAN非対応で×」とした製品が使える可能性がある。

### ★最重要: 更新運用の現実性

この案件のコアは「マニュアルが育つ」こと。技術的にQ&Aができるだけでは不十分で、
**市の担当者（非エンジニア）がWordを差し替えるだけで知識ベースが更新される**レベルでないと、
結局年1回更新に逆戻りし、元の課題と何も変わらない。

RAGの知識ベース更新は見た目のシンプルさに反して厄介:
- チャンク分割の再計算（章構成が変わると精度がガタ落ち）
- 古い情報の残留リスク（バージョン管理）
- 更新後の精度検証（誰がどうやるか）

→ **「更新運用をどこまでサービス側が吸収してくれるか」が選定の分水嶺**

## 詳細評価

### ◎ 本命: 既製品SaaS（PKSHA、LoGoチャット等）

**概要**: 自治体向けに開発された日本語AIチャットボット製品。FAQ管理・ダッシュボード・サポートが一体。

**なぜ本命か**:
- 自治体での豊富な導入実績 → 調達時の説明がしやすい
- 非エンジニアが管理画面からドキュメント追加・削除可能
- **更新運用がサービスに内包されている**（チャンク戦略等はベンダー側が管理）
- ITリテラシーに差があるスタッフでも使えるUI
- 月10〜30万円は自治体の予算感に合う
- LGWAN対応製品あり（LoGoチャット等）

**候補製品**:
| 製品 | 特徴 |
|------|------|
| LoGoチャット | J-LIS系、LGWAN対応。自治体特化 |
| PKSHA ChatAgent | 国内シェアNo.1。Teams連携可。国交省導入実績 |
| さっとFAQ | 低コスト、中小自治体向け |
| OfficeBot | RAG型。PDF/Wordそのまま投入可。千代田区実績 |

**懸念点**:
- 「フィードバック循環」（Q&Aログ→マニュアル改善提案）の仕組みは標準搭載されていない可能性
- カスタマイズ性は自前構築より低い
- 指定管理者向け（外部ユーザー）のアクセス設計が標準対応しているか要確認

### ○ 対抗: LINE WORKS + AI連携

**概要**: 業務チャットLINE WORKS上でAIチャットボット連携。LINEライクなUI。

**強み**:
- **UIの親しみやすさが圧倒的** — 「LINEで聞く」感覚で使える
- 横浜市で粗大ごみ申請にLINE+チャットボット運用実績あり（月額19万円、年間25万件）
- 事務所スタッフの定着率が最も高くなりそう

**懸念点**:
- ISMAP未登録 → セキュリティポリシー上の承認が必要
- 個人情報を扱わない前提ならインターネット系での運用は可能
- RAGの知識ベース更新をどう組み込むかは追加開発が必要

### ○ 有力: Azure OpenAI + RAG（ASPサービス経由）

**概要**: GaiXer等のLGWAN-ASP対応サービス経由でAzure OpenAI + RAGを利用。

**強み**:
- 技術的自由度が最も高い
- GaiXerはISMAP-LIU登録・LGWAN ASP登録済み
- 横浜市のRAG実証もAzure系（NTT東日本伴走）

**懸念点**:
- 構築にSI費用が必要（数百万円〜）
- **更新運用は自前で設計が必要** ← ここが最大のリスク
- 市の担当者だけでは運用できない → 保守契約が必須

### △ PoC向け: Dify（ノーコードRAG）

**概要**: OSSのノーコードRAGプラットフォーム。PDF投入だけで動く。

**強み**:
- **予算確保前のプロトタイプ検証に最速**
- 無料で「こういうことができます」をデモできる
- 本番は別の選択肢に移行する前提でOK

**懸念点**:
- 自治体での実績なし → 本番採用は難しい
- セキュリティ審査の説明責任が重い

### △ 条件付き: M365 Copilot

**概要**: SharePoint上のドキュメントをCopilotが参照して回答。

**強み**:
- 市がM365を使っていれば追加投資が小さい
- SharePointにマニュアルを置くだけ → 更新は簡単

**懸念点**:
- **指定管理者の事務所にM365環境がなければ使えない** ← 致命的
- **本市CopilotはSharePointに対応していない** ← 致命的
- Q&Aチャットボットとしてのカスタマイズ性が低い
- エスカレーション機能は別途構築が必要

### × 不適: オンプレLLM

GPU調達・運用保守を自治体が自前で行うのは非現実的。却下。

## 推奨戦略

### PoC: NotebookLM（近日解禁見込み）

横浜市はGoogleと提携済み。NotebookLMは未解禁だが近い将来使えるようになる見込み。
PoCツールとしてNotebookLMが最適な理由：
- 市の既存提携の延長 → **新規サービス導入の承認プロセスを回避**
- 市の担当者が自分でPDFを投入して質問するだけ → 技術者不要
- 「こういうことができる」を体感してもらう目的には十分

**NotebookLMの限界（PoCとして割り切る）**:
- Q&Aログの蓄積・分析ができない → フィードバック循環は検証できない
- エスカレーションフロー・権限管理がない → 本番運用には使えない
- 指定管理者への提供手段がない → あくまで市側の内部検証用

```
PoC（NotebookLM）: マニュアル1〜2章で「体感」→ 庁内合意形成
  ↓ 予算確保・方針決定
本番選定: 以下から1つ
  A. 既製品SaaS（OfficeBot or PKSHA）← 運用重視・更新容易性重視
  B. Azure系ASP（GaiXer等）← カスタマイズ・フィードバック循環重視
  C. LINE WORKS + AI ← 現場定着重視
  ↓
フィードバック循環の実装
  Q&Aログ分析→更新提案の仕組みは、どの選択肢でも追加開発が必要
```
