# 制約整理：役所 × 指定管理者の関係性

## 1. 指定管理者制度の基本構造

### 法的根拠
- **地方自治法 第244条の2 第3項**
- 公の施設の管理を、条例の定めにより法人その他の団体に行わせることができる

### 市と指定管理者の関係

```
横浜市（設置者・監督者）
  │
  ├── 基本協定書（包括的な管理運営ルール）
  ├── 年度協定書（各年度の業務仕様・予算）
  ├── 仕様書（業務の具体的内容）
  └── マニュアル（手続きの詳細手順）← ★ここが対象
  │
  ▼
指定管理者（受託者・実務執行者）
  └── 事務所（現場で住民対応）
```

### 権限構造の特徴

| 項目 | 市 | 指定管理者 |
|------|-----|-----------|
| 制度設計 | ○ 決定権あり | × 提案のみ |
| マニュアル作成 | ○ 作成・承認 | △ 意見は出せる |
| 日常運用 | △ 監督 | ○ 実務執行 |
| 判断の裁量 | ○ 最終判断 | △ マニュアル範囲内 |
| 住民対応 | △ エスカレーション受け | ○ 一次対応 |

**核心的な構造問題**:
市が作るマニュアル ≠ 現場の実態。しかし現場の声が市に届くチャネルが弱い。

## 2. この案件固有の制約

### 共用部分代行管理制度とは
- 横浜市の市営住宅等の共用部分（廊下、階段、エレベーター等）の管理を代行する制度
- 指定管理者事務所が住民からの問い合わせ・修繕依頼等を受ける
- 手続きの種類が多く、判断基準が複雑

### 現場で起きている問題（docxより）
1. **事務所が独自解釈で対応** → 市のルールと乖離
2. **市への確認ハードルが高い** → 電話しか手段がない
3. **市は問題発生まで気づけない** → 事後対応になる
4. **マニュアル更新が年1回** → 現場の知見が反映されない

## 3. AIソリューション導入時の制約

### 自治体IT制約

| 制約 | 内容 | 影響 |
|------|------|------|
| **LGWAN** | 自治体の閉域ネットワーク | クラウドLLMへのアクセス制限の可能性 |
| **個人情報保護条例** | 住民情報の外部送信制限 | AIへの入力データに個人情報を含めない設計必須 |
| **クラウド利用基準** | ISMAPや自治体セキュリティポリシー | 利用可能なサービスが限定される |
| **調達ルール** | 公共調達の透明性・公平性 | 随意契約の上限、プロポーザルの手続き |
| **予算サイクル** | 年度単位の予算編成 | 年度途中の追加は困難 |

### 指定管理者側の制約

| 制約 | 内容 | 影響 |
|------|------|------|
| **ITリテラシー** | 事務所スタッフのスキル差 | UIは極力シンプルに |
| **業務端末** | 市から貸与？自前？ | アプリインストールの可否 |
| **業務時間** | 住民対応の合間に使う | 即座に回答が返る必要あり |
| **複数事業者** | 指定管理者が変わる可能性 | 事業者に依存しない設計 |

### 導入の法的リスク

- **AIの回答＝市の公式見解になるか？** → 免責の仕組みが必要
- **誤回答による住民への影響** → エスカレーション必須、回答の正確性担保
- **マニュアル更新の法的位置づけ** → 市の承認プロセスを経ない自動更新は不可

## 4. 制約から導かれる設計原則

1. **AIは「参考回答」であり「市の指示」ではない** → 免責表示必須
2. **個人情報はAIに入力しない** → 質問テンプレート化、匿名化
3. **マニュアル更新は市が承認** → 自動提案→人間レビュー→反映のフロー
4. **既存インフラを最大限活用** → Teams/SharePoint等、新規導入を最小化
5. **事業者交代に耐える設計** → 知識はシステム側に蓄積、事業者非依存
6. **段階的導入** → まずPoCから、小規模で効果を実証してから展開
