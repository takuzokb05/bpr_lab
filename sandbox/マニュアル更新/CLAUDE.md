# マニュアル更新AIハブ — 調査・設計プロジェクト

## WHY

横浜市の共用部分代行管理制度において、市と指定管理者事務所の間に「認識のずれ」が構造化している。
年1回のマニュアル配布では現場の判断ミスを防げず、市も問題発生まで気づけない。
AIチャットボットを介した双方向フィードバック循環で、この構造を変えたい。

**現在フェーズ: 調査・構想段階**

## WHAT — プロジェクト構造

```
マニュアル更新/
├── CLAUDE.md                  ← このファイル（プロジェクト方針）
├── 育てるマニュアル：…….docx   ← 元の相談資料
├── research/                  ← 調査結果
│   ├── constraints.md         ← 役所・指定管理者の制約整理
│   ├── tech-options.md        ← 技術選定（RAG/チャットボット比較）
│   ├── similar-cases.md       ← 自治体AI活用の先行事例
│   └── legal-procurement.md   ← 調達・法的制約（個人情報保護等）
├── design/                    ← 設計ドキュメント
│   ├── architecture.md        ← システム構成案
│   ├── user-flows.md          ← 利用者フロー（事務所/市/AI）
│   └── mvp-scope.md           ← MVP定義・段階的導入計画
└── docs/                      ← 提案・報告用
    └── proposal-draft.md      ← 提案書ドラフト
```

## HOW — 調査方針

### ステークホルダーと制約

| 主体 | 役割 | 主な制約 |
|------|------|---------|
| **横浜市**（発注者） | マニュアル作成・制度設計 | 自治体調達ルール、個人情報保護条例、予算制約 |
| **指定管理者事務所**（利用者） | 住民対応・日常運用 | ITリテラシー差、独自判断の慣習、業務時間制約 |
| **住民** | 制度の最終受益者 | 直接は使わないが品質に影響を受ける |

### 調査すべき論点

1. **制度的制約**
   - 指定管理者制度（地方自治法244条の2）の権限範囲
   - 市と指定管理者の責任分界点（マニュアル＝市の指示 vs 運用裁量）
   - 個人情報保護（住民情報がAIに流れるリスク）
   - 自治体のクラウドサービス利用ガイドライン（LGWAN等）

2. **技術選択肢**
   - RAG（検索拡張生成）ベースのQ&Aシステム
   - ルールベース＋LLMハイブリッド
   - Microsoft 365 Copilot（自治体向けライセンス）
   - LINE/Teams等の既存チャネル活用
   - オンプレミス vs クラウド（自治体セキュリティ基準）

3. **運用設計**
   - エスカレーションフロー（AI→市への判断依頼）
   - マニュアル更新の承認プロセス（自動更新は危険→市が承認）
   - ログ分析→改善提案の仕組み
   - 事務所ごとの利用格差をどう埋めるか

4. **先行事例**
   - 自治体×AIチャットボット（住民向けは多数、職員向けは少ない）
   - 指定管理者×ナレッジ管理の事例
   - マニュアル自動更新の実現手法

### 調査の進め方

```
Phase A: 制約整理（今ここ）
  → 役所側の制約・指定管理者制度の特性を明確化
  → constraints.md にまとめる

Phase B: 技術調査
  → 制約に合致する技術選択肢を比較
  → tech-options.md + similar-cases.md

Phase C: 設計・提案
  → MVP定義、段階的導入計画
  → proposal-draft.md
```

## 重要な前提

- **マニュアルの自動更新は「自動提案→市が承認」であるべき**（市の責任範囲）
- **住民の個人情報はAIに入力しない設計**が必須
- 指定管理者は複数事業者の可能性あり→マルチテナント考慮
- 市の既存IT基盤（Teams? LGWAN?）を活用できるかが費用に大きく影響
