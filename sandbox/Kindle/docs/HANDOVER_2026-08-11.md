## ③ 確定事実（すべて実測で確認済み）

### Kindleアプリの前提が変わった

- **レガシー版 Kindle for PC は 2026-06-30 にサーバ側で無効化済み**。どのバージョンでも認証が通らない
- レガシー版 2.8.3 / 2.9.1 は Snapdragon X（ARM64）で**起動直後にクラッシュ**する（既知の未修正バグ）
- **解決策 = Microsoft Store版「Amazon Kindle: Reading App」**（ID `9P8JQ0JJSTLL` / x86版がPrismで動作）
  - 「ARM機はStore版非対応」という6月頃の報道は古い。実機でインストール・動作を確認済み
- Store版の実行ファイル名も `Kindle.exe` なので `window_manager.py` の検出はそのまま通る
- **Store版はウィンドウタイトルが常に `Kindle`** で書名を含まない（→ 書名OCR改修の動機）

### 撮影の前提

- **開始位置は「本文1ページ目」ではなく「表紙」**。表紙の手前まで戻さないと
  `detectPageTurnDirection` が `ambiguous` を返して停止する（安全装置が正しく働いた結果であり、バグではない）
- **マウス位置は撮影結果に一切影響しない**。本文中央/右下隅/本文左上の3か所で撮影して全て完全一致。
  カーソルは写り込まず、Kindle側のホバー描画も起きない。`activateWindow` はマウスを動かしていない
  （例外: `--manual-turn` は意図的にクリックする）

### OCR環境

- Tesseract 5.4.0 は `C:\Program Files\Tesseract-OCR`（jpn同梱）。**PATHには通っていない**が
  `ocr.py` の `_findTesseract()` が既定パスを拾うので動く
- **実行しているのはシステムPython 3.13.7**（venvではない）。ここに ocrmypdf が無かったのが
  「OCR利用不可」の原因。導入時の副作用: pillow 10.4.0→12.3.0 / pdfplumber 0.11.8→0.11.10 / pdfminer.six更新
- `pip check` に残る protobuf 警告（tensorflow / ortools）は本件と無関係の既存事象

### NotebookLM側の性質（重要な発見）

- **NotebookLMはページ画像を読んでいる**。表紙の背景色「水色」を正答したことで確定
  （色はOCRテキスト層に残らないため、テキストからは導出不可能）
- **図の中の文字もテキスト層に入る**。Tesseractはページ全体を画像としてOCRするため、
  図表内のラベル（研究開発/商品設計/生産/流通/広告・販売 等）は検索可能テキストになっている
- 制限値: **1ソース200MBまたは50万ワード**（プラン共通）。ソース数のみ無料50 / Plus100 / Pro300
- 回答精度は高いが、**「2〜3週間で完遂」など本文に存在しない記述を返した例あり**（数値・期間は要裏取り）

### 今回の改修（コミット済み）

- `pdf_engine.py`: `JPEG_QUALITY = 80` で埋め込み。一時ディレクトリで変換し撮影済みPNGは不変。
  1枚の変換失敗は元画像にフォールバックして全滅を防ぐ。`jpegQuality=None` で従来のPNGに戻せる
- `ocr.py`: `extractHeaderTitle()` / `detectBookTitleFromPages()` を追加。ページ上部6%をOCRし、
  **2ページ以上で一致した場合のみ採用**（ヘッダーが無いページでは `'Tie OOO Ley) hn'` のような
  誤読が検証を素通りする実測があったため、一致を必須にした）
- `main.py`: `resolveBookTitle()` を追加。ウィンドウタイトルが汎用名のときだけヘッダーOCRを使い、
  それも失敗したら手入力を促す
- 検収: **pytest 104件全pass**（28件追加）/ ruff・mypy クリーン / `main.py --help` 起動確認

### OCR速度の実測（24ページで計測 / 10コア機）

| 設定 | 所要 | 174ページ換算 |
|---|---|---|
| `--jobs 1` | 242.6秒 | 29.3分 |
| `--jobs 4` | 45.6秒 | 5.5分 |
| `--jobs 8` | 30.6秒 | 3.7分 |
| 既定（現状・未指定） | 27.6秒 | 3.3分 |

- **ocrmypdfは既に全10コアを使っている**。並列数の調整による時短余地は無い
- `tesseract.exe` も `python.exe` も **x64バイナリでPrismエミュレーション実行**。
  ARM64ネイティブ版は Windows向け公式配布が見当たらず、自前ビルドは労力に見合わない
- `tessdata_fast` への変更は可能だが、現状でも誤読があるため**精度を下げる方向は非推奨**

## ④ 未解決の問い

   - PDF生成後、OCRをワーカースレッドに投入して即座に次の本の撮影へ
   - 撮影中のOCRは `--jobs 8`（2コアを撮影側に温存。実測コストは11%のみ）
