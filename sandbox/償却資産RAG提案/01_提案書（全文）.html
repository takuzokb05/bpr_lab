Chapter 01

1. 要旨

償却資産税業務において、RAG（Retrieval-Augmented Generation: 検索拡張生成）技術を活用し、調査・審査・事業者対応の効率化と品質向上を実現することを提案する。デジタル統括本部が来年度より開始する手上げ制RAG導入支援に応募し、3つのユースケースで導入を目指す。さらに、担当者の異動に左右されず知識が育ち続けるエコシステムを構築し、組織としての知見を永続化する。

Chapter 02

2. 背景と課題

2.1 業務環境の変化

2025年度に新基幹システムを導入した。同システムは資産データを5年分遡及して保持し、過去の申告漏れを検出する機能を備えている。しかし、現状ではデータの保持にとどまり、蓄積データの高度な活用には至っていない。

加えて、新システムの安定化に想定以上の工数を要しており、2026年度以降も通常業務の負荷が高い状態が続く見込みである。

2.2 構造的課題

課題影響
専任職の知見が属人化異動により精査品質が低下
大量申告データの手動チェック全件確認が不可能、課税漏れリスク
事業者からの問い合わせが電話に集中繁忙期の対応負荷が過大、回答品質にばらつき
新システムの蓄積データが未活用投資対効果が限定的
知識の更新が属人的担当者異動のたびにリセットされるリスク

2.3 なぜ今か — 次年度がラストチャンス

  • 専任職のタイムリミット: A専任職（元SE、技術的に推進力がある）とM専任職（次年度で定年見込み）が在籍しているのは次年度まで。この2人がいるうちに知見をナレッジベースに移す必要がある
  • デジタル統括本部のRAG導入支援が来年度から開始される（手上げ制）
  • 本市にRAGの実績あり: 選挙管理でRAG実証実験を実施済み。庁内にノウハウが蓄積されており、ゼロからの立ち上げではない
  • 他都市の事例も増加中（草津市・神戸市等、第7章参照）。自治体RAGの環境が整いつつある
  • 新システムにより5年分のデータ基盤が整った
  • 通常業務が忙しいからこそ、調査系業務の効率化が不可欠

次年度を逃すと、M専任職の定年退職により知見の一部が不可逆的に失われる。

Chapter 03

3. 提案内容

3.1 ユースケース1: 大規模家屋 見積精査AI

対象業務: 1,000m2以上の事業用建物に対する大規模家屋調査の見積精査

現状:

  • 調査前に見積書・図面を精査し、評価額の目星をつける
  • 評価要領の理解と専任職レベルの経験知が必要
  • 精査に数時間を要し、経験の浅い職員は見落としリスクが高い

RAG導入後:

  • 評価要領・専任職のノウハウ・過去事例をナレッジベース化
  • 見積書・図面を入力すると、精査ポイントと概算評価を提示
  • 初期精査時間の大幅短縮（数時間 → 30分〜1時間）
  • 知見が異動に左右されず蓄積・継承される

3.2 ユースケース2: 申告データ疑義抽出AI

対象業務: 電子申告・紙申告データの疑義チェック（家屋疑義・自動車・申告不要資産の抽出）

現状:

  • 大量の義務者データから手作業で疑義を確認
  • 全件目視チェックは現実的に不可能
  • 見逃しは課税漏れ・過大課税につながる

RAG導入後:

  • 申告データCSVを一括読み込み、判定基準に基づき自動分類
  • 自動車・少額減価償却等の機械的判定はルールベース、家屋疑義等の専門判断が必要なものはRAGで判定基準を参照する2層構成
  • 疑義フラグ・理由・優先度を付与したリストを出力
  • 全件スクリーニングが可能となり、課税公平性が向上
  • 新システムの5年遡及データと組み合わせ、過去の申告漏れも検出

3.3 ユースケース3: 事業者向け問い合わせチャットボット

対象業務: 事業者（申告義務者）からの問い合わせ対応

現状:

  • 電話がファーストコンタクトで、定型的な質問にも職員が直接対応
  • 繁忙期（1〜3月）に問い合わせが集中し、対応負荷が跳ね上がる
  • 回答品質が担当者の経験に依存

RAG導入後:

  • 申告の手引き・FAQ・耐用年数表等をナレッジベース化
  • チャットボットが一次対応し、定型質問を自動回答
  • AIが判断できない質問は職員にエスカレーション
  • 問い合わせログが自動蓄積され、FAQ改善の根拠になる

回答信頼度の3段階運用:

段階説明対応
明確に回答可能ナレッジに該当記載ありAIが回答、ログ記録
判断が必要類似記載はあるが完全一致しない職員に確認を案内
回答不可該当記載なし窓口・電話への誘導
Chapter 04

4. 知識更新エコシステム — 異動に耐える仕組み

RAG導入の最大のリスクは、ナレッジベースの陳腐化である。担当者の異動サイクル（通常3〜5年）を考えると、特定の人に依存しない更新の仕組みが不可欠である。

4.1 設計思想: 業務の副産物としてナレッジが育つ

3つのユースケースが共通のナレッジベースを利用し、日常業務の中で自然に知識が蓄積・更新される循環を構築する。

  • UC-1（見積精査）: 新たな精査ポイントの発見 → ナレッジに追加
  • UC-2（疑義抽出）: 新たな疑義パターンの発見 → 判定基準に追加
  • UC-3（チャットボット）: AIが回答できなかった質問 → 職員回答後にナレッジ追加

4.2 運用原則

原則内容
承認は必ず人が行うAIの自動更新は禁止。職員が内容を確認してから反映
更新は小さく頻繁に年1回の大改訂ではなく、気づいた時に1件ずつ追加
専門スキル不要管理画面からドキュメント追加できるSaaSを選定
引継ぎコスト最小化知識はシステムに蓄積済み。引継ぐのは「承認フロー」だけ

4.3 異動サイクルへの耐性

従来は異動のたびに知識がリセットされていたが、エコシステムにより逆の効果が生まれる:

  • 1年目（後任A）: 前任の知見 + 自分の知見 → ナレッジに蓄積
  • 2年目（後任B）: 蓄積済みナレッジで即戦力 → さらに追加
  • 3年目以降: 知識が組織に残り、異動のたびに強くなる
Chapter 05

5. 新システムとの相乗効果

新基幹システムへの投資を最大限に活かす観点からも、RAG導入は合理的である。

新システムの価値 = データ保持（実現済み） × データ活用（← RAGが担う）
観点新システム単体新システム + RAG
データ保持5年分蓄積同左
データ活用手動確認のみ自動スクリーニング・知見検索
投資回収限定的データ活用による業務効率化で回収

6.1 共通ナレッジ基盤

3つのユースケースが共有する基盤データ:

データ入手元優先度
償却資産税評価要領庁内必須

6.2 ユースケース別データ

UC-1（見積精査）:

  • 過去の評価資料（匿名化が必要）

UC-3（チャットボット）:

  • 申告の手引き・記載例（事業者配布物）
  • FAQ（既存があればそのまま活用）
  • 過去の問い合わせ対応記録

申告データCSVをそのまま投入する際の注意:

ノイズ対策

Chapter 09

9. 精度保証と運用ルール

9.1 基本原則: AI出力は必ず職員が最終確認する

RAGは「補助ツール」であり、最終判断は職員が行う。これは全UCに共通の大原則とする。

9.2 UC別の精度基準と運用ルール

UC精度の考え方運用ルール
UC-1（見積精査）AIは精査ポイントの「候補」を提示。見落とし防止が目的であり、AIの概算をそのまま採用しない職員が独立に精査した上で、AIの指摘を追加チェックとして活用
UC-2（疑義抽出）全件スクリーニングが目的。偽陽性（疑義なしを疑義ありと判定）は許容、偽陰性（見逃し）を最小化AIが抽出したリストを職員が確認。AIが「問題なし」としたものも抜き打ちで検証
UC-3（チャットボット）回答信頼度3段階で運用。「明確に回答可能」のみ自動回答、それ以外は職員にエスカレーション免責表示「本回答は参考情報です。正式な判断は窓口にお問い合わせください」を全回答に付与

9.3 誤回答時の対応

  • UC-1/UC-2: 職員の最終確認が前提のため、AI誤出力の責任は生じない（従来の手作業と同じ責任構造）
  • UC-3: 免責表示を付与。万一AIの誤回答により事業者が不利益を受けた場合に備え、Phase 3開始前に法務担当（総務局法制課等）への事前相談を必須とする。相談時には免責表示案・回答信頼度の3段階設計・誤回答時の対応フローを持参すること

9.4 Phase 1 PoCでの精度検証

Phase 1で以下を計測し、Phase 2移行の判断材料とする:

指標基準（Go/No-Go）
UC-2の疑義検出率既知の疑義事例の80%以上を検出できるか
UC-2の偽陽性率職員の確認負荷が現状を上回らないか
PoC工数想定の1.5倍以内で完了するか

Go: 基準達成 → Phase 2（本格構築）へ
Conditional Go: 一部未達 → スコープ縮小して継続（UC-2のみに集中等）
No-Go: 全指標未達 → SaaS切替を検討、または中止

9.5 Phase 1の副次的効果 — PoCは「知識の棚卸し」でもある

Phase 1の価値は精度検証だけではない。PoCの過程そのものが、属人化した知識を組織知に変える機会になる。

  • AIに評価要領を読ませて質問すると、「この回答は合っているか？」を専任職に確認する場面が必然的に生まれる。この会話自体が知識移転
  • AIが出した疑義リストを職員が確認する過程で、「なぜこれが疑義なのか」の判定基準が言語化される
  • AIが間違えたケースを議論すると、評価要領に書かれていない暗黙のルール（専任職の頭の中にしかないもの）が炙り出される

たとえAIの精度が期待値に達しなくても、棚卸しの過程で得られた知見はそのまま組織の資産になる。PoCに工数を割くリスクに対する保険でもある。

Chapter 10

10. 実現可能性

10.1 技術面

  • 評価要領・判定基準はPDF/Word形式 → RAGのドキュメントローダーで取り込み可能
  • 申告データはCSV形式 → 構造化データとして即時利用可能
  • 草津市のkopo等、固定資産税特化のSaaSも選択肢
  • デジタル統括本部の支援によりインフラ・セキュリティ面の課題をクリア可能
  • 本市は選挙管理でRAG実証実験の実績あり — 庁内にノウハウが蓄積されている

10.2 人材面

  • A専任職は元SE（転職組） — 技術的な議論ができ、RAG導入の共同推進者として期待できる
  • 後任担当者はNotebookLM（Google製AIツール）の利用経験あり
  • プロトタイプ検証をNotebookLMで実施し、効果を確認してから本格導入も可能
  • デジタル統括本部の技術支援を受けられる手上げ制のため、部署単独での技術力は必須ではない

10.3 段階的導入

フェーズ内容期間目安Go/No-Go基準
Phase 1NotebookLMでPoC（UC-2）1〜2ヶ月疑義検出率80%以上
Phase 2デジ統括と本格RAG構築（UC-1, UC-2）3〜6ヶ月Phase 1基準達成
Phase 3UC-3（チャットボット）追加・エコシステム確立6ヶ月〜Phase 2安定運用

※Phase 1不調時の選択肢: SaaS切替（kopo等）、スコープ縮小、中止

14. データ匿名化の手順

14.1 申告データCSV

申告データCSVには宛名番号が含まれるが、宛名番号単体では個人を特定できない。ただし本市のセキュリティルールに準拠し、以下の匿名化を行ってからNotebookLMにアップロードする。

Excelマクロで一括処理する手順:

  1. CSVをExcelで開く
  2. 以下の列を処理:
    • 宛名番号 → 連番（1, 2, 3, ...）に置換
    • 義務者名（あれば） → 削除
    • 住所（あれば） → 削除
    • その他、個人・法人を特定できる列 → 削除
  3. 処理済みCSVを別名で保存（元データは残す）

※Pythonは不要。Excelの置換機能またはVBAマクロで対応可能。マクロのテンプレートは必要に応じてデジタル統括本部に相談。

14.2 過去の評価資料

  • 義務者名・住所を黒塗りまたは削除
  • 物件を特定できる情報（地番等）も削除が望ましい
  • 残すべき情報: 構造・面積・評価額・精査ポイント（ノウハウの本体）

14.3 評価要領・判定基準

  • 公開情報・庁内規程のため匿名化不要
  • そのままPDFとしてアップロード可能

15. Phase 1 PoC 実施手順

15.1 準備するもの

#データ件数・量準備方法
1匿名化済み申告データCSVまず100件程度第14章の手順で匿名化
2償却資産税評価要領（PDF）全文庁内サーバーからダウンロード
3家屋評価要領（PDF）全文同上
4既知の疑義事例リスト10〜20件過去に実際に発見した家屋疑義・自動車・申告不要資産をリストアップ

15.2 NotebookLMでの検証手順

Step 1: ノートブック作成

  1. NotebookLMにアクセスし、新しいノートブックを作成
  2. ソースとして評価要領PDF・家屋評価要領PDFをアップロード
  3. 匿名化済みCSVをGoogleスプレッドシートに変換してアップロード（CSVのまま直接アップロードも可）

Step 2: 基本動作の確認

  1. まず評価要領に対して簡単な質問を投げる（例:「1,000m2以上の大規模家屋調査の手順は？」）
  2. 回答がソースに基づいているか確認（引用元が表示される）
  3. この段階で精度に問題があればソースの品質を疑う（→ RAG入門ガイドのトラブルシューティング参照）

Step 3: 疑義抽出の検証

  1. 正解データに含まれる疑義事例のCSVをアップロード
  2. 質問例: 「このCSVの中で、家屋に該当する可能性がある資産はどれですか？判定理由も示してください」
  3. AIの回答と正解データを突き合わせ、検出率を計測

Step 4: 結果の記録

計測項目記録方法
検出率（再現率）正解20件中、AIが何件検出したか
偽陽性の件数AIが疑義ありと判定したが実際は問題ない件数
回答の質判定理由が妥当か（A専任職に評価してもらう）
所要時間準備〜検証〜結果整理にかかった時間

15.3 注意事項

  • NotebookLMはスプレッドシート2,000行程度で処理が遅くなる。まず100件で試し、問題なければ段階的に増やす
  • 大量のCSVを一括で疑義判定させるのは苦手。バッチ分割（100件ずつ） で処理する
  • 大量出力が必要な場合はGeminiとの連携を検討（NotebookLMを知識ベースとして参照し、Gemini側でタスク実行）
  • CSVに非申告資産が混在しているとノイズになる。事前にExcelフィルタで明らかな非申告資産を除外しておく

15.4 Go/No-Go判定

第9.4章の基準で判定する。判定は後任が行い、結果を課長に報告する。

16. 結論

償却資産税業務へのRAG導入は、以下5点から推進すべきである:

  1. 知見の永続化: 専任職の経験知を組織資産として蓄積し、異動で失われない
  2. 業務効率化: 調査系業務と事業者対応の負荷を軽減し、忙しい中でも回る体制に
  3. 投資回収: 新システムの蓄積データをRAGで活用し、システム投資の効果を最大化
  4. 持続可能性: 知識更新エコシステムにより、担当者が替わっても知識が育ち続ける
  5. 展開可能性: 償却資産で築いた基盤は土地・家屋・他税目に横展開でき、税部門全体のDXの起点となる

Phase 1（NotebookLMでのPoC）は実質無料で着手可能であり、閑散期の5〜10人日で実施できる。デジタル統括本部の手上げ制が開始され次第、速やかに応募することを推奨する。

償却資産税が税畑のファーストペンギンとなり、固定資産税全体、そして税部門全体のDXの礎を築く。
