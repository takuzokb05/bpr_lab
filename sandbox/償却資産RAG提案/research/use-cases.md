# ユースケース詳細

## UC-1: 大規模家屋 見積精査AI

### 現状の課題

- 1,000m2以上の事業用建物は必ず現地調査を実施（大規模家屋調査）
- 調査前に見積書・図面を精査し、評価額の目星をつける必要がある
- 見積精査には評価要領の深い理解と専任職レベルの経験知が必要
- 経験の浅い職員は精査に時間がかかり、見落としリスクも高い
- 専任職の知見は属人化しており、異動で失われやすい

### RAGで実現すること

**ナレッジベース（蓄積するもの）:**
- 固定資産評価基準（家屋）
- 評価要領（自治体独自の運用基準）
- 専任職の精査ノウハウ（チェックポイント、よくある見落とし）
- 過去の調査事例（匿名化済み）

**入力:**
- 見積書PDF
- 図面（平面図・立面図等）

**出力:**
- 精査すべきポイントの一覧
- 概算評価額の目安
- 見積書と評価要領の乖離箇所の指摘
- 類似過去事例の参照

### 期待効果

| 指標 | Before | After（見込み） |
|------|--------|-----------------|
| 見積精査時間 | 1物件あたり数時間 | 初期精査30分〜1時間 |
| 見落としリスク | 経験依存 | チェックリスト自動生成で低減 |
| 知見の継承 | 異動で喪失 | RAGに蓄積・永続化 |

### 技術的実現性

- 評価要領はPDF/Word → RAGのドキュメントローダーで対応可能
- 見積書PDFはOCR+構造化が必要 → マルチモーダルLLMで図面読み取りも視野
- NotebookLMでプロトタイプ検証が可能（後任が使い慣れている）

## UC-2: 申告データ疑義抽出AI

### 現状の課題

- 電子申告・紙申告（本市様式）の資産データをシステムに登録
- 大量の義務者（申告者）のデータから以下を手作業で確認:
  - **家屋疑義**: 償却資産として申告されているが家屋評価すべきもの
  - **自動車**: 償却資産の対象外（軽自動車税の対象）
  - **申告不要資産**: 少額減価償却資産等、申告対象外のもの
- 義務者数が多く、全件目視チェックは現実的に不可能
- 見逃すと課税漏れや過大課税のリスク

### RAGで実現すること

**ナレッジベース（蓄積するもの）:**
- 家屋疑義の判定基準（建物附属設備の取扱い等）
- 自動車・軽自動車の判定ルール
- 少額減価償却資産の基準
- 過去の疑義抽出事例・是正パターン

**入力:**
- 申告データCSV（資産名称、取得価額、耐用年数、数量等）

**出力:**
- 疑義フラグ付きリスト（家屋疑義 / 自動車 / 申告不要 / 要確認）
- 疑義理由の説明（根拠条文・判定基準を引用）
- 優先度ランク（影響額ベース）

### 期待効果

| 指標 | Before | After（見込み） |
|------|--------|-----------------|
| 疑義チェック | 手作業で一部のみ | 全件スクリーニング可能 |
| 抽出精度 | 担当者の経験依存 | 判定基準の統一適用 |
| 課税漏れリスク | 見逃しあり | 網羅的チェックで低減 |

### 技術的実現性

- CSVデータは構造化済み → LLMでの分類タスクに適している
- ルールベース（耐用年数・資産名称パターン）+ RAG（判断基準参照）の組み合わせ
- 新システムの5年遡及データと組み合わせれば、過去申告漏れも検出可能

## UC-3: 事業者向け問い合わせチャットボット

### 現状の課題

- 事業者（申告義務者）からの問い合わせは電話が主なファーストコンタクト
- 「何を申告すればいいか」「耐用年数はどうなるか」等、定型的な質問が多い
- 繁忙期（1〜3月の申告期）に問い合わせが集中し、職員の対応負荷が跳ね上がる
- 回答品質が担当者の経験に依存し、異動後に品質がばらつく

### RAGで実現すること

**ナレッジベース（蓄積するもの）:**
- 申告の手引き・記載例
- よくある質問と回答（FAQ）
- 耐用年数表・資産分類表
- 過去の問い合わせ対応事例（匿名化済み）

**入力:**
- 事業者からのテキスト質問（チャットUI経由）

**出力:**
- 回答（根拠条文・手引きの該当箇所を引用）
- 回答信頼度の段階表示:
  - 明確に回答可能 → そのまま参考にしてもらう
  - 関連記載はあるが判断が必要 → 職員に確認を案内
  - 回答不可 → 窓口・電話への誘導

### エスカレーション設計

```
事業者                    AI                      職員
  |                       |                       |
  |-- 質問 ------------->|                       |
  |                       |-- 回答可能 ---------->| （ログのみ）
  |<-- 回答 -------------|                       |
  |                       |                       |
  |                       |-- 判断が必要 -------->|
  |                       |                       |-- 確認・回答
  |<-- 職員の回答 --------|<-- 回答を返却 ---------|
  |                       |                       |
  |                       |   回答をナレッジに追加  |
  |                       |   （職員が承認後）      |
```

### 期待効果

| 指標 | Before | After（見込み） |
|------|--------|-----------------|
| ファーストコンタクト | 電話のみ | チャットで24時間対応可能 |
| 定型質問の対応負荷 | 職員が全件対応 | AIが一次対応、職員は判断案件に集中 |
| 回答品質 | 担当者依存 | ナレッジベースで統一 |
| 問い合わせログ | 蓄積なし | 自動蓄積 → FAQ改善の根拠に |

### 技術的実現性

- 手引き・FAQ等はPDF/Word → RAGで取り込み可能
- チャットボットSaaS（PKSHA ChatAgent、OfficeBot等）が自治体向けに実績あり
- 非エンジニアが管理画面からドキュメント追加・更新可能な製品を選定すれば運用負荷は低い
- NotebookLMで回答精度のPoC検証が可能

### 参考: マニュアル更新PJの知見

別プロジェクト（指定管理者向けマニュアル更新）で同様のチャットボット+循環設計を検討済み:
- 回答信頼度の3段階分け → そのまま償却資産にも適用可能
- 質問ログの改善活用 → FAQの継続的更新に活用
- 既製品SaaSの活用 → 更新運用がサービス側に内包される利点

## 3つのユースケースの関係

```
UC-1（大規模家屋）: 専門知識の民主化   → 調査品質の底上げ
UC-2（疑義抽出）  : 大量データの自動分類 → 課税公平性の向上
UC-3（チャットボット）: 事業者対応の自動化 → 職員負荷軽減 + 住民サービス向上

共通基盤: RAGナレッジベース（評価要領・判定基準・FAQ・過去事例）
         ↑ 3つのUCが同じナレッジを共有・育てる
```

## 知識更新エコシステム — 「人が変わっても回る仕組み」

### 課題: RAGの最大のリスクは陳腐化

RAGを導入しても、ナレッジベースが更新されなければ数年で使い物にならなくなる。
担当者の異動サイクル（通常3〜5年）を考えると、特定の人に依存しない更新の仕組みが不可欠。

### 設計: 業務の中で自然にナレッジが育つ循環

```
         ┌─────────────────────────────────────┐
         |         ナレッジベース（RAG）          |
         |  評価要領 / 判定基準 / FAQ / 事例     |
         └──────┬──────────────┬────────────────┘
                |              |
     ┌──────────▼──┐    ┌─────▼──────────┐
     | UC-1 見積精査 |    | UC-2 疑義抽出   |
     | UC-3 チャット |    |                |
     └──────┬───────┘    └─────┬──────────┘
            |                  |
            ▼                  ▼
     ┌──────────────────────────────────┐
     |        業務利用ログの蓄積          |
     |  - AIが答えられなかった質問        |
     |  - 職員が修正した回答             |
     |  - 新たに発見した疑義パターン      |
     └──────────────┬───────────────────┘
                    |
                    ▼
     ┌──────────────────────────────────┐
     |     職員が承認 → ナレッジに反映     |
     |  （AIの自動更新は禁止。必ず人が承認）|
     └──────────────┬───────────────────┘
                    |
                    └───→ ナレッジベースに戻る（循環）
```

### エコシステムの設計原則

| 原則 | 内容 |
|------|------|
| **業務の副産物として育つ** | 「更新作業」を別途やるのではなく、日常業務のログが改善の種になる |
| **承認は必ず人が行う** | AIの自動更新は禁止。誤った知識の混入を防ぐ |
| **更新は小さく頻繁に** | 年1回の大改訂ではなく、気づいた時に1件ずつ追加 |
| **属人化しない運用** | 管理画面からドキュメント追加できるSaaSを選定。専門スキル不要 |
| **異動の引継ぎコスト最小化** | 知識はシステムに蓄積済み。引継ぐのは「承認フロー」だけ |

### 異動サイクルへの耐性

```
1年目（後任A）: 前任の知見 + 自分の知見 → ナレッジに蓄積
  ↓ 異動
2年目（後任B）: ナレッジベースに1年分の蓄積あり → 即戦力で業務開始
  ↓ 異動
3年目（後任C）: 2年分の蓄積 → さらに充実
  ...
知識が組織に残り、異動のたびに強くなる
```

## 新システムとの相乗効果

新システムが5年分のデータを保持している点は、RAG導入の強い追い風:

1. **データはある** → 新システムが蓄積済み
2. **活用手段がない** → 現状は手動確認のみ
3. **RAGが橋渡し** → 蓄積データ × 判定知識 = 自動スクリーニング

「データを保持しているだけではもったいない。RAGで活用してこそ新システム投資の回収になる」
