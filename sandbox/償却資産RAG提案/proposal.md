# 償却資産税業務へのRAG導入提案書

## 1. 要旨

償却資産税業務において、RAG（Retrieval-Augmented Generation: 検索拡張生成）技術を活用し、調査・審査・事業者対応の効率化と品質向上を実現することを提案する。デジタル統括本部が来年度より開始する手上げ制RAG導入支援に応募し、3つのユースケースで導入を目指す。さらに、担当者の異動に左右されず知識が育ち続けるエコシステムを構築し、組織としての知見を永続化する。

---

## 2. 背景と課題

### 2.1 業務環境の変化

2025年度に新基幹システムを導入した。同システムは資産データを5年分遡及して保持し、過去の申告漏れを検出する機能を備えている。しかし、現状ではデータの保持にとどまり、蓄積データの高度な活用には至っていない。

加えて、新システムの安定化に想定以上の工数を要しており、2026年度以降も通常業務の負荷が高い状態が続く見込みである。

### 2.2 構造的課題

| 課題 | 影響 |
|------|------|
| 専任職の知見が属人化 | 異動により精査品質が低下 |
| 大量申告データの手動チェック | 全件確認が不可能、課税漏れリスク |
| 事業者からの問い合わせが電話に集中 | 繁忙期の対応負荷が過大、回答品質にばらつき |
| 新システムの蓄積データが未活用 | 投資対効果が限定的 |
| 知識の更新が属人的 | 担当者異動のたびにリセットされるリスク |

### 2.3 なぜ今か — 次年度がラストチャンス

- **専任職のタイムリミット**: A専任職（元SE、技術的に推進力がある）とM専任職（次年度で定年見込み）が在籍しているのは次年度まで。この2人がいるうちに知見をナレッジベースに移す必要がある
- デジタル統括本部のRAG導入支援が来年度から開始される（手上げ制）
- **本市にRAGの実績あり**: 選挙管理でRAG実証実験を実施済み。庁内にノウハウが蓄積されており、ゼロからの立ち上げではない
- 他都市の事例も増加中（草津市・神戸市等、第7章参照）。自治体RAGの環境が整いつつある
- 新システムにより5年分のデータ基盤が整った
- **通常業務が忙しいからこそ、調査系業務の効率化が不可欠**

**次年度を逃すと、M専任職の定年退職により知見の一部が不可逆的に失われる。**

## 3. 提案内容

### 3.1 ユースケース1: 大規模家屋 見積精査AI

**対象業務:** 1,000m2以上の事業用建物に対する大規模家屋調査の見積精査

**現状:**
- 調査前に見積書・図面を精査し、評価額の目星をつける
- 評価要領の理解と専任職レベルの経験知が必要
- 精査に数時間を要し、経験の浅い職員は見落としリスクが高い

**RAG導入後:**
- 評価要領・専任職のノウハウ・過去事例をナレッジベース化
- 見積書・図面を入力すると、精査ポイントと概算評価を提示
- 初期精査時間の大幅短縮（数時間 → 30分〜1時間）
- 知見が異動に左右されず蓄積・継承される

### 3.2 ユースケース2: 申告データ疑義抽出AI

**対象業務:** 電子申告・紙申告データの疑義チェック（家屋疑義・自動車・申告不要資産の抽出）

**現状:**
- 大量の義務者データから手作業で疑義を確認
- 全件目視チェックは現実的に不可能
- 見逃しは課税漏れ・過大課税につながる

**RAG導入後:**
- 申告データCSVを一括読み込み、判定基準に基づき自動分類
- 自動車・少額減価償却等の機械的判定はルールベース、家屋疑義等の専門判断が必要なものはRAGで判定基準を参照する2層構成
- 疑義フラグ・理由・優先度を付与したリストを出力
- 全件スクリーニングが可能となり、課税公平性が向上
- 新システムの5年遡及データと組み合わせ、過去の申告漏れも検出

### 3.3 ユースケース3: 事業者向け問い合わせチャットボット

**対象業務:** 事業者（申告義務者）からの問い合わせ対応

**現状:**
- 電話がファーストコンタクトで、定型的な質問にも職員が直接対応
- 繁忙期（1〜3月）に問い合わせが集中し、対応負荷が跳ね上がる
- 回答品質が担当者の経験に依存

**RAG導入後:**
- 申告の手引き・FAQ・耐用年数表等をナレッジベース化
- チャットボットが一次対応し、定型質問を自動回答
- AIが判断できない質問は職員にエスカレーション
- 問い合わせログが自動蓄積され、FAQ改善の根拠になる

**回答信頼度の3段階運用:**

| 段階 | 説明 | 対応 |
|------|------|------|
| 明確に回答可能 | ナレッジに該当記載あり | AIが回答、ログ記録 |
| 判断が必要 | 類似記載はあるが完全一致しない | 職員に確認を案内 |
| 回答不可 | 該当記載なし | 窓口・電話への誘導 |

## 4. 知識更新エコシステム — 異動に耐える仕組み

RAG導入の最大のリスクは、ナレッジベースの陳腐化である。担当者の異動サイクル（通常3〜5年）を考えると、特定の人に依存しない更新の仕組みが不可欠である。

### 4.1 設計思想: 業務の副産物としてナレッジが育つ

3つのユースケースが共通のナレッジベースを利用し、日常業務の中で自然に知識が蓄積・更新される循環を構築する。

- **UC-1（見積精査）**: 新たな精査ポイントの発見 → ナレッジに追加
- **UC-2（疑義抽出）**: 新たな疑義パターンの発見 → 判定基準に追加
- **UC-3（チャットボット）**: AIが回答できなかった質問 → 職員回答後にナレッジ追加

### 4.2 運用原則

| 原則 | 内容 |
|------|------|
| 承認は必ず人が行う | AIの自動更新は禁止。職員が内容を確認してから反映 |
| 更新は小さく頻繁に | 年1回の大改訂ではなく、気づいた時に1件ずつ追加 |
| 専門スキル不要 | 管理画面からドキュメント追加できるSaaSを選定 |
| 引継ぎコスト最小化 | 知識はシステムに蓄積済み。引継ぐのは「承認フロー」だけ |

### 4.3 異動サイクルへの耐性

従来は異動のたびに知識がリセットされていたが、エコシステムにより逆の効果が生まれる:

- **1年目（後任A）**: 前任の知見 + 自分の知見 → ナレッジに蓄積
- **2年目（後任B）**: 蓄積済みナレッジで即戦力 → さらに追加
- **3年目以降**: 知識が組織に残り、異動のたびに強くなる

## 5. 新システムとの相乗効果

新基幹システムへの投資を最大限に活かす観点からも、RAG導入は合理的である。

```
新システムの価値 = データ保持（実現済み） × データ活用（← RAGが担う）
```

| 観点 | 新システム単体 | 新システム + RAG |
|------|---------------|-----------------|
| データ保持 | 5年分蓄積 | 同左 |
| データ活用 | 手動確認のみ | 自動スクリーニング・知見検索 |
| 投資回収 | 限定的 | データ活用による業務効率化で回収 |

## 6. 着手に必要なデータ

### 6.1 共通ナレッジ基盤

3つのユースケースが共有する基盤データ:

| データ | 入手元 | 優先度 |
|--------|--------|--------|
| 償却資産税評価要領 | 庁内 | 必須 |
| 家屋評価要領 | 庁内 | 必須（「家屋でなければ償却」の判定根拠） |
| 固定資産評価基準（総務省告示） | 総務省 | 必須 |
| 課税標準の特例一覧（最新） | 庁内/総務省 | 必須（毎年改正あり） |
| 関連条例・規則 | 例規集 | 必須 |
| 総務省通知・通達 | 庁内 | 高 |

### 6.2 ユースケース別データ

**UC-1（見積精査）:**
- 過去の評価資料（匿名化が必要）
- 専任職の精査ノウハウ（**異動前の収集が急務**）
- 見積書の構造パターン、耐用年数表

**UC-2（疑義抽出）:**
- 申告データCSV（**要クリーニング** — 非申告資産が混在するとノイズになる）
- 家屋疑義・自動車・少額減価償却の各判定基準
- 過去の疑義抽出・是正事例

**UC-3（チャットボット）:**
- 申告の手引き・記載例（事業者配布物）
- FAQ（既存があればそのまま活用）
- 過去の問い合わせ対応記録

### 6.3 CSVデータのクリーニング

申告データCSVをそのまま投入する際の注意:

| ノイズ | 対策 |
|--------|------|
| 非申告資産の混在 | 事前フィルタリングまたはフラグ付与 |
| 過年度の重複 | 最新年度のみ or 年度カラムで管理 |
| 表記揺れ（エアコン/空調機/ルームエアコン等） | 名寄せルール or LLMで正規化 |

**推奨**: まず義務者100件程度でPoC → ノイズパターン洗い出し → クリーニングルール確立 → 全件投入

## 8. コスト概算

### 8.1 導入方式の比較

| 項目 | A: SaaS活用 | B: デジ統括と自前構築 | C: ハイブリッド |
|------|------------|---------------------|----------------|
| UC-1（見積精査） | kopo等の既製品 | RAG自前構築 | SaaS |
| UC-2（疑義抽出） | 対応製品が少ない | RAG自前構築 | 自前構築 |
| UC-3（チャットボット） | PKSHA等の既製品 | RAG自前構築 | SaaS |
| 初期費用 | 低（数十万〜） | 中〜高（200〜500万） | 中 |
| 月額費用 | 中（15〜50万/月） | 低（API利用料中心） | 中 |
| 年間ランニング | 200〜600万/年 | 50〜150万/年 | 150〜400万/年 |
| 構築負荷 | 低 | 高（デジ統括の支援前提） | 中 |
| カスタマイズ性 | 低〜中 | 高 | 中〜高 |

※上記は一般的な市場相場に基づく概算。デジタル統括本部の支援範囲（技術のみか、インフラ・予算含むか）により大幅に変動する可能性あり

**参考相場（2025〜2026年時点）:**
- RAG構築（PoC〜本番）: 50〜200万（PoC）、300〜1,000万（本番導入）
- 自治体向けAIチャットボットSaaS: 初期20〜100万、月額15〜50万
- LLM API利用料: 月額数千〜数万円（利用量による）

### 8.2 推奨: ハイブリッド方式（C案）

UC-2（CSVの疑義抽出）は既製SaaSでは対応困難なため自前構築が必要。一方、UC-1（評価要領検索）はkopo等のSaaSで対応可能な領域、UC-3（チャットボット）も既製品の方が運用負荷が低い。

**SaaSで済む部分はSaaSを使い、自前構築は本当に必要な部分に絞る。**

### 8.3 費用対効果（粗い試算）

| 効果項目 | 試算根拠 | 推定削減時間/年 | 人件費換算（参考） |
|---------|---------|---------------|-------------------|
| 見積精査の短縮（UC-1） | 年20件×1件3時間短縮 | 約60時間 | 約18万円 |
| 疑義チェックの全件化（UC-2） | 手作業チェック年200時間と仮定、70%自動化 | 約140時間 | 約42万円 |
| 定型問い合わせの自動化（UC-3） | 神戸市実績65%自動回答を参考、問い合わせ対応年300時間と仮定 | 約195時間 | 約59万円 |
| **合計** | | **約395時間** | **約119万円** |

※人件費単価は3,000円/時で試算。総務省「地方公務員給与実態調査」ベースでは5,000〜7,000円/時程度となり、その場合は年間198〜277万円相当の効果となる。後任が実態に合わせて補正すること
※上記は直接的な時間削減のみ。課税漏れ防止・知見永続化等の定性的効果は含まない

**逆算ロジック**: 年間120万円相当の効果が見込めるため、ランニングコストが年120万円以下であれば投資回収可能。デジ統括の支援によりコストが抑えられれば、初年度から効果が上回る可能性がある

※正確な費用対効果はPhase 1 PoC完了後に算出。現時点では「概算コストはデジ統括の支援次第で50〜400万/年の幅がある」という水準感を示す

## 9. 精度保証と運用ルール

### 9.1 基本原則: AI出力は必ず職員が最終確認する

RAGは「補助ツール」であり、最終判断は職員が行う。これは全UCに共通の大原則とする。

### 9.2 UC別の精度基準と運用ルール

| UC | 精度の考え方 | 運用ルール |
|----|------------|-----------|
| UC-1（見積精査） | AIは精査ポイントの「候補」を提示。見落とし防止が目的であり、AIの概算をそのまま採用しない | 職員が独立に精査した上で、AIの指摘を追加チェックとして活用 |
| UC-2（疑義抽出） | 全件スクリーニングが目的。偽陽性（疑義なしを疑義ありと判定）は許容、偽陰性（見逃し）を最小化 | AIが抽出したリストを職員が確認。AIが「問題なし」としたものも抜き打ちで検証 |
| UC-3（チャットボット） | 回答信頼度3段階で運用。「明確に回答可能」のみ自動回答、それ以外は職員にエスカレーション | 免責表示「本回答は参考情報です。正式な判断は窓口にお問い合わせください」を全回答に付与 |

### 9.3 誤回答時の対応

- UC-1/UC-2: 職員の最終確認が前提のため、AI誤出力の責任は生じない（従来の手作業と同じ責任構造）
- UC-3: 免責表示を付与。万一AIの誤回答により事業者が不利益を受けた場合に備え、**Phase 3開始前に法務担当（総務局法制課等）への事前相談を必須とする**。相談時には免責表示案・回答信頼度の3段階設計・誤回答時の対応フローを持参すること

### 9.4 Phase 1 PoCでの精度検証

Phase 1で以下を計測し、Phase 2移行の判断材料とする:

| 指標 | 基準（Go/No-Go） |
|------|-----------------|
| UC-2の疑義検出率 | 既知の疑義事例の80%以上を検出できるか |
| UC-2の偽陽性率 | 職員の確認負荷が現状を上回らないか |
| PoC工数 | 想定の1.5倍以内で完了するか |

**Go**: 基準達成 → Phase 2（本格構築）へ
**Conditional Go**: 一部未達 → スコープ縮小して継続（UC-2のみに集中等）
**No-Go**: 全指標未達 → SaaS切替を検討、または中止

### 9.5 Phase 1の副次的効果 — PoCは「知識の棚卸し」でもある

Phase 1の価値は精度検証だけではない。**PoCの過程そのものが、属人化した知識を組織知に変える機会になる。**

- AIに評価要領を読ませて質問すると、「この回答は合っているか？」を専任職に確認する場面が必然的に生まれる。この会話自体が知識移転
- AIが出した疑義リストを職員が確認する過程で、「なぜこれが疑義なのか」の判定基準が言語化される
- AIが間違えたケースを議論すると、評価要領に書かれていない暗黙のルール（専任職の頭の中にしかないもの）が炙り出される

つまり**たとえAIの精度が期待値に達しなくても、棚卸しの過程で得られた知見はそのまま組織の資産になる**。PoCに工数を割くリスクに対する保険でもある。

## 10. 実現可能性

### 10.1 技術面

- 評価要領・判定基準はPDF/Word形式 → RAGのドキュメントローダーで取り込み可能
- 申告データはCSV形式 → 構造化データとして即時利用可能
- 草津市のkopo等、固定資産税特化のSaaSも選択肢
- デジタル統括本部の支援によりインフラ・セキュリティ面の課題をクリア可能
- **本市は選挙管理でRAG実証実験の実績あり** — 庁内にノウハウが蓄積されている

### 10.2 人材面

- **A専任職は元SE（転職組）** — 技術的な議論ができ、RAG導入の共同推進者として期待できる
- 後任担当者はNotebookLM（Google製AIツール）の利用経験あり
- プロトタイプ検証をNotebookLMで実施し、効果を確認してから本格導入も可能
- デジタル統括本部の技術支援を受けられる手上げ制のため、部署単独での技術力は必須ではない

### 10.3 段階的導入

| フェーズ | 内容 | 期間目安 | Go/No-Go基準 |
|---------|------|---------|--------------|
| Phase 1 | NotebookLMでPoC（UC-2） | 1〜2ヶ月 | 疑義検出率80%以上 |
| Phase 2 | デジ統括と本格RAG構築（UC-1, UC-2） | 3〜6ヶ月 | Phase 1基準達成 |
| Phase 3 | UC-3（チャットボット）追加・エコシステム確立 | 6ヶ月〜 | Phase 2安定運用 |

※Phase 1不調時の選択肢: SaaS切替（kopo等）、スコープ縮小、中止
※UC-3（チャットボット）は既製品SaaS活用で構築負荷を抑える

### 10.4 エコシステムの運用負荷

| 作業 | 頻度 | 想定工数 |
|------|------|---------|
| ナレッジ追加の承認 | 随時（月5〜10件想定） | 1件あたり10〜15分 |
| 定期棚卸し（品質監査） | 年1回 | 2〜3人日 |
| 法改正対応 | 年1〜2回 | 1〜2人日/回 |

**フォールバック策**: 更新が3ヶ月滞った場合、デジタル統括本部に運用支援を要請。最悪のケースでも法改正がなければナレッジは1年程度は有効（評価要領・判定基準は年度単位の改正）

## 11. 展開可能性 — 税部門のファーストペンギン

### 11.1 償却資産から固定資産税全体へ

償却資産税でRAGの実績を作れば、同じ固定資産税の枠内で横展開が可能:

| 展開先 | 共有できるナレッジ | 追加で必要なデータ |
|--------|-------------------|-------------------|
| **土地評価** | 評価基準、条例規則、通知通達 | 路線価、地目認定基準、画地計算法 |
| **家屋評価** | 家屋評価要領（既にUC-1で整備済み） | 再建築費評点基準表、経年減点補正 |
| **納税者対応全般** | FAQ、チャットボット基盤（UC-3） | 土地・家屋の問い合わせパターン |

**共通ナレッジ基盤の投資が、償却だけでなく土地・家屋にも効く。**

### 11.2 他税目・他部署への波及

| 波及先 | 可能性 |
|--------|--------|
| 市民税（個人・法人） | 問い合わせチャットボットの横展開 |
| 収納部門 | 滞納整理のナレッジベース化 |
| 他部署（福祉・建築等） | RAG/チャットボット基盤の共有利用 |

### 11.3 なぜ償却資産が最適な起点か

1. **データが構造化済み**: 申告データCSVがそのまま使える（土地・家屋より着手しやすい）
2. **ナレッジの共有範囲が広い**: 評価要領・家屋要領は土地・家屋と共通
3. **リスクが相対的に低い**: 大規模家屋調査は件数が限定的でPoCに適している
4. **後任にAIリテラシーがある**: NotebookLM経験者が着任予定

**償却資産で成功すれば、そのナレッジ基盤・エコシステム・運用ノウハウがそのまま税部門全体のDXの礎になる。**

## 12. リスクと対策

| リスク | 対策 |
|--------|------|
| 通常業務の負荷が高く着手できない | Phase 1はNotebookLMで小規模検証（想定工数: 5〜10人日）。7〜9月の閑散期に集中実施 |
| 精度が不十分 | Phase 1でGo/No-Go判定（第9.4章）。税務はAI出力を必ず職員が最終確認（第9.1章） |
| AI誤回答で事業者が不利益を受ける | UC-3に免責表示を付与。運用開始前に法務担当に相談（第9.3章） |
| 個人情報・税務情報の取扱い | 申告データCSVは宛名番号のみで個人特定は不可能だが、本市ルールに準拠し匿名化してからアップロード（第14章参照）。過去評価資料は名前列を削除。本格導入時はデジタル統括本部のセキュリティ基準に準拠 |
| ナレッジが陳腐化する | エコシステム設計（第4章）+ 定期棚卸し年1回 + 3ヶ月滞留でエスカレーション |
| コストが想定を超える | ハイブリッド方式でSaaS/自前を最適配分（第8.2章）。Phase 1は実質無料（NotebookLM） |
| 手上げ制の詳細が未確定 | 2026年度にデジタル統括本部が機構改革予定。窓口が変わる可能性があるため、制度発表前でも非公式に「こういう取組を検討中」と打診しておく（第13章参照） |
| 後任がAIに懐疑的/使えない | 引継ぎ時にNotebookLMデモ実施（30分）。使わなくても従来業務に支障なし（フォールバック） |
| 見積書・図面のOCR精度が不足する | 新システムのOCRは申告書のみ対応。デジタル統括本部提供のOCRツールを活用。精度不足時は手動転記でフォールバック |

## 14. データ匿名化の手順

### 14.1 申告データCSV

申告データCSVには宛名番号が含まれるが、宛名番号単体では個人を特定できない。ただし本市のセキュリティルールに準拠し、以下の匿名化を行ってからNotebookLMにアップロードする。

**Excelマクロで一括処理する手順:**

1. CSVをExcelで開く
2. 以下の列を処理:
   - 宛名番号 → 連番（1, 2, 3, ...）に置換
   - 義務者名（あれば） → 削除
   - 住所（あれば） → 削除
   - その他、個人・法人を特定できる列 → 削除
3. 処理済みCSVを別名で保存（元データは残す）

※Pythonは不要。Excelの置換機能またはVBAマクロで対応可能。マクロのテンプレートは必要に応じてデジタル統括本部に相談。

### 14.2 過去の評価資料

- 義務者名・住所を黒塗りまたは削除
- 物件を特定できる情報（地番等）も削除が望ましい
- 残すべき情報: 構造・面積・評価額・精査ポイント（ノウハウの本体）

### 14.3 評価要領・判定基準

- 公開情報・庁内規程のため匿名化不要
- そのままPDFとしてアップロード可能

## 15. Phase 1 PoC 実施手順

### 15.1 準備するもの

| # | データ | 件数・量 | 準備方法 |
|---|--------|---------|---------|
| 1 | 匿名化済み申告データCSV | まず100件程度 | 第14章の手順で匿名化 |
| 2 | 償却資産税評価要領（PDF） | 全文 | 庁内サーバーからダウンロード |
| 3 | 家屋評価要領（PDF） | 全文 | 同上 |
| 4 | 既知の疑義事例リスト | 10〜20件 | 過去に実際に発見した家屋疑義・自動車・申告不要資産をリストアップ |

### 15.2 NotebookLMでの検証手順

**Step 1: ノートブック作成**
1. NotebookLMにアクセスし、新しいノートブックを作成
2. ソースとして評価要領PDF・家屋評価要領PDFをアップロード
3. 匿名化済みCSVをGoogleスプレッドシートに変換してアップロード（CSVのまま直接アップロードも可）

**Step 2: 基本動作の確認**
1. まず評価要領に対して簡単な質問を投げる（例:「1,000㎡以上の大規模家屋調査の手順は？」）
2. 回答がソースに基づいているか確認（引用元が表示される）
3. この段階で精度に問題があればソースの品質を疑う（→ RAG入門ガイドのトラブルシューティング参照）

**Step 3: 疑義抽出の検証**
1. 正解データに含まれる疑義事例のCSVをアップロード
2. 質問例: 「このCSVの中で、家屋に該当する可能性がある資産はどれですか？判定理由も示してください」
3. AIの回答と正解データを突き合わせ、検出率を計測

**Step 4: 結果の記録**

| 計測項目 | 記録方法 |
|---------|---------|
| 検出率（再現率） | 正解20件中、AIが何件検出したか |
| 偽陽性の件数 | AIが疑義ありと判定したが実際は問題ない件数 |
| 回答の質 | 判定理由が妥当か（A専任職に評価してもらう） |
| 所要時間 | 準備〜検証〜結果整理にかかった時間 |

### 15.3 注意事項

- **NotebookLMはスプレッドシート2,000行程度で処理が遅くなる**。まず100件で試し、問題なければ段階的に増やす
- 大量のCSVを一括で疑義判定させるのは苦手。**バッチ分割（100件ずつ）** で処理する
- 大量出力が必要な場合は**Geminiとの連携を検討**（NotebookLMを知識ベースとして参照し、Gemini側でタスク実行）
- CSVに非申告資産が混在しているとノイズになる。事前にExcelフィルタで明らかな非申告資産を除外しておく

### 15.4 Go/No-Go判定

第9.4章の基準で判定する。判定は後任が行い、結果を課長に報告する。

## 16. 結論

償却資産税業務へのRAG導入は、以下5点から推進すべきである:

1. **知見の永続化**: 専任職の経験知を組織資産として蓄積し、異動で失われない
2. **業務効率化**: 調査系業務と事業者対応の負荷を軽減し、忙しい中でも回る体制に
3. **投資回収**: 新システムの蓄積データをRAGで活用し、システム投資の効果を最大化
4. **持続可能性**: 知識更新エコシステムにより、担当者が替わっても知識が育ち続ける
5. **展開可能性**: 償却資産で築いた基盤は土地・家屋・他税目に横展開でき、税部門全体のDXの起点となる

Phase 1（NotebookLMでのPoC）は実質無料で着手可能であり、閑散期の5〜10人日で実施できる。デジタル統括本部の手上げ制が開始され次第、速やかに応募することを推奨する。

**償却資産税が税畑のファーストペンギンとなり、固定資産税全体、そして税部門全体のDXの礎を築く。**
