01 RAGアーキテクチャの全体像

RAG（Retrieval-Augmented Generation）は、LLM単体の知識に頼らず、外部知識ベースから関連情報を検索してからLLMに生成させるパイプラインアーキテクチャである。パラメトリック知識（LLMの学習済み重み）とノンパラメトリック知識（ベクトルDB等の外部ストア）を組み合わせることで、ハルシネーションを抑制し、根拠の追跡を可能にする。

RAGの進化段階

本案件での位置づけ

PoCフェーズ（Phase 1）はNaive RAGでよい。NotebookLMがそれにあたる。しかし本格構築ではAdvanced RAGまで踏み込む必要がある。理由は明確で、評価要領の家屋疑義判定は文書内の複数箇所を横断的に参照する判断（例: 建物附属設備の定義＋課税客体の範囲＋個別通達）であり、単純なTop-K検索では必要なコンテキストを取りこぼす。Modular RAGまでは不要 — コスト・運用負荷に見合わない。

NotebookLMの位置づけ: GoogleがホスティングするNaive RAGサービス。内部ではGeminiのエンベディング + ベクトル検索 + Gemini生成を使っている。ユーザーが制御できるのはソースドキュメントの選択とプロンプトのみ。チャンキング戦略、エンベディングモデル、検索パラメータ（Top-K等）は一切変更不可。これが「PoCとしては十分だが、本格構築には不足」と言う理由。

02 チャンキング戦略 — 評価要領に最適な分割

RAGの精度は「どうチャンクを切るか」で大きく変わる。LLMのコンテキストウィンドウに収まるサイズに文書を分割する必要があるが、分割の仕方によって検索精度が著しく変動する。

チャンキング手法の比較

手法 分割ロジック 長所 短所 適合度
Fixed-size N文字ごとに機械的分割 実装が最も簡単 文の途中で切れる。意味的まとまりが破壊される 低
Sentence-based 文末（。）で分割し、N文ごとにチャンク化 文の途中で切れない 段落・節の構造を無視。法規文書の「ただし書き」が本文と分離する 中
Semantic エンベディングの類似度変化点で分割 意味的に一貫したチャンク 計算コスト高。チャンクサイズが不均一 中
Recursive 文書構造（章→節→項→号）を優先し、サイズ超過時に再帰的に下位レベルで分割 法規文書の構造を保持。階層メタデータも付与可能 文書構造の解析が必要。マークアップが前提 高

なぜRecursive Splittingか

評価要領の構造を考える。

第3章 課税客体
  第1節 償却資産の範囲
    第1項 総則
      (1) 土地及び家屋以外の事業の用に供することができる資産で…
        ア 構築物
          (ア) 煙突、焼却炉、鉄塔、…
        イ 機械及び装置
      (2) 次に掲げる資産は、償却資産に含まれないものとする。
        ア 自動車税又は軽自動車税の課税客体であるもの
        イ 無形減価償却資産
    第2項 家屋と償却資産の区分    ← 家屋疑義判定の核心
      (1) 家屋の定義
      (2) 建物附属設備の取扱い
        ア 家屋に含めるもの
          (ア) 電気設備（屋内配線に限る）
          (イ) 給排水設備（…）
        イ 償却資産とするもの
          (ア) 受変電設備
          (イ) 特定の業種の用に供する設備

この階層構造をFixed-sizeで切ると、「(2) 建物附属設備の取扱い」の冒頭定義と「イ 償却資産とするもの」が別チャンクに分離する。検索時に片方しかヒットせず、判定に必要な文脈が欠落する。

Recursive Splittingでは、まず「第2項」単位でチャンク化を試み、サイズ超過の場合にのみ(1)(2)レベルに分割する。さらに各チャンクに階層メタデータ（chapter: 3, section: 1, paragraph: 2）を付与することで、検索時にメタデータフィルタリングと組み合わせられる。

パラメータの目安

パラメータ 推奨値 根拠
チャンクサイズ 512〜1024トークン 小さすぎると文脈が不足（検索ノイズ増加）。大きすぎるとTop-Kで無関係な情報が混入しFaithfulnessが低下。経験的にこの範囲がバランスが良い
オーバーラップ 64〜128トークン 隣接チャンクとの接続点で文脈の断絶を緩和する。「ただし」「この場合において」等の接続がチャンク境界を跨ぐケースの対策
Top-K 5〜10 家屋疑義は複数箇所を横断参照する。K=3では不足する場合が多い。ただしKを増やすとノイズも増えるため、リランキングとの併用が前提
NotebookLMの制約: NotebookLMは内部で自動チャンキングを行うが、手法・サイズ・オーバーラップのいずれもユーザーが制御できない。PoCでは「ソースの入れ方」で間接的に誘導する（章ごとに別ファイルとしてアップロードする等）のが限界。本格構築フェーズで自前チャンキングに切り替えることで、ここの精度が劇的に変わる。

03 エンベディングモデルの選定

エンベディングはテキストを高次元ベクトルに変換する処理であり、RAGの検索精度を根本的に規定する。日本語の税務ドメインにおいて、どのモデルが適切かを検討する。

候補モデル比較

モデル 提供元 次元数 日本語性能 コスト 備考
text-embedding-3-small OpenAI 1536 良好 $0.02/1Mトークン コスパ最良。MATSAベンチで日本語上位
text-embedding-3-large OpenAI 3072 非常に良好 $0.13/1Mトークン 精度重視の場合。次元削減オプションあり
text-embedding-004 Google 768 良好 無料枠あり / $0.025/1Mトークン NotebookLMが内部使用。Vertex AI経由で利用可
multilingual-e5-large Microsoft 1024 非常に良好 オープンソース（無料） ローカル実行可。MTEBベンチ上位。ただしGPU推奨
intfloat/multilingual-e5-large-instruct Microsoft 1024 非常に良好 オープンソース instruction-tunedで検索タスクに強い。e5-largeの上位互換
cl-nagoya/sup-simcse-ja-large 名大NLP 1024 日本語特化 オープンソース 日本語STS高精度。ただし多言語非対応

税務用語のドメイン適合性

一般的なベンチマーク（MTEB等）ではWikipediaやニュース記事での評価が主であり、税務ドメイン固有の用語に対する性能は別途検証が必要。具体的に問題になる用語:

用語 困難な理由
家屋疑義 一般語彙に存在しない複合語。「疑義」の税務的ニュアンス（家屋か償却資産かの判断が分かれるもの）
課税標準の特例 「特例」が汎用語すぎて他の法律（所得税、法人税等）の特例と混同
建物附属設備 「附属」の旧字体。新字体「付属」との表記揺れ
少額資産 / 一括償却資産 金額要件が文脈依存（10万/20万/30万の閾値が制度によって異なる）
非課税 / 課税免除 / 減免 法的には全て異なる概念だが、ベクトル空間上で近接する可能性が高い

推奨

  • Phase 1（NotebookLM）: 選択の余地なし。Google内部のエンベディングが使われる。
  • Phase 2（Gemini API）: text-embedding-004 をまず使用。NotebookLMとの比較がしやすい（同系統のモデル）。精度不足時に text-embedding-3-small（OpenAI）へ切替を検討。
  • Phase 3（自前構築）: multilingual-e5-large-instruct をローカルまたはCloud Run上で実行。ドメイン適合性が不足する場合、税務文書コーパスでファインチューニングを検討（ただし費用対効果の見極めが必要）。
ファインチューニングの現実: エンベディングモデルのファインチューニングには正例・負例のペアデータセット（最低数百件）が必要。税務ドメインでこれを整備するコストは無視できない。まずは汎用モデル + プロンプトエンジニアリング + リランキングで対処し、それでも精度が出ない場合の最終手段と位置づける。

04 UC-2の実装設計 — ルールベース × RAGの2層構成

申告書CSVの全行をLLMに投げるのは非効率かつ不正確。確定的に判定できるもの（自動車、少額資産等）はルールベースで先に処理し、RAGはルールでは判断できないグレーゾーン（家屋疑義等）にのみ適用する。

Layer 1 — Rule-Based Filter

確定的判定（ルールベース）

以下はLLM不要。パターンマッチと数値比較で100%の精度が出る:

  • 自動車判定: 資産名称に「自動車」「トラック」「フォークリフト（大型特殊）」等 → 自動車税対象の可能性フラグ
  • 少額判定: 取得価額 < 10万円 → 少額資産（免税点以下）
  • 非申告資産: 耐用年数経過済み or 除却済みフラグ
  • 明らかな構築物・機械装置: キーワード辞書によるカテゴリ分類

本市ルール Python実行不可。GAS or Excel VBAで実装する。

Layer 2 — RAG判定

グレーゾーン判定（LLM必要）

Layer 1で確定しなかった残りの行に対して、評価要領をナレッジベースとしたRAG判定を実行:

  • 家屋疑義判定: 建物附属設備の家屋/償却の区分
  • 特殊設備: テナント設置の内装・空調は家屋か償却か
  • 複合資産: 太陽光発電設備、蓄電池等の新しいカテゴリ

各行をクエリとして評価要領チャンクを検索し、根拠付きで判定。

Layer 1 実装例（GAS）

本市ルール 業務PCではPython実行環境がないため、Google Apps Script（GAS）で実装する。スプレッドシートのデータに対して直接処理可能。

/**
 * Layer 1: ルールベースフィルタ
 * 申告書データの各行に対して確定的判定を行う
 * 判定不能な行は "要RAG判定" フラグを立てる
 */
function applyRuleFilter() {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName("申告データ");
  const data = sheet.getDataRange().getValues();
  const header = data[0];

  // 列インデックス特定
  const colName = header.indexOf("資産名称");
  const colAmount = header.indexOf("取得価額");
  const colResult = header.indexOf("L1判定");
  const colFlag = header.indexOf("RAG要否");

  // キーワード辞書
  const VEHICLE_KEYWORDS = ["自動車", "トラック", "バス", "フォークリフト"];
  const THRESHOLD_SMALL = 100000; // 10万円

  for (let i = 1; i < data.length; i++) {
    const name = String(data[i][colName]);
    const amount = Number(data[i][colAmount]);
    let result = "";
    let needRAG = false;

    // Rule 1: 自動車判定
    if (VEHICLE_KEYWORDS.some(kw => name.includes(kw))) {
      result = "自動車税対象の可能性";
    }
    // Rule 2: 少額判定
    else if (amount < THRESHOLD_SMALL) {
      result = "少額資産（10万未満）";
    }
    // Rule 3: 明確な償却資産カテゴリ
    else if (/^(サーバ|コンピュータ|プリンタ|複合機)/.test(name)) {
      result = "器具備品（確定）";
    }
    // 判定不能 → RAGへ
    else {
      result = "判定保留";
      needRAG = true;
    }

    sheet.getRange(i + 1, colResult + 1).setValue(result);
    sheet.getRange(i + 1, colFlag + 1).setValue(needRAG ? "要" : "");
  }
}

Layer 2 実装パターン（Gemini API）

Layer 1で「要RAG判定」となった行を、Gemini APIに投入する。NotebookLMでは手動コピペが必要だが、APIならバッチ処理が可能。

/**
 * Layer 2: Gemini APIによるRAG判定（GAS版）
 * 前提: 評価要領チャンクをスプレッドシートの別シートに格納済み
 *       または Vertex AI Search のデータストアに投入済み
 *
 * ※ 簡易版。本格構築ではVertex AI Searchのグラウンディングを使う
 */
function queryGeminiForRAG(assetName, assetDetail) {
  const API_KEY = PropertiesService.getScriptProperties().getProperty("GEMINI_API_KEY");
  const endpoint = `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.0-flash:generateContent?key=${API_KEY}`;

  // 評価要領の関連チャンクを事前に取得（簡易: キーワードマッチ）
  const relevantChunks = findRelevantChunks(assetName);

  const prompt = `あなたは償却資産税の専門家です。
以下の資産が「家屋の一部」か「償却資産」かを判定してください。

【資産情報】
資産名称: ${assetName}
詳細: ${assetDetail}

【評価要領（関連箇所）】
${relevantChunks}

【出力形式】
判定: [家屋 / 償却資産 / 要確認]
根拠条文: [該当する評価要領の条項番号]
信頼度: [高 / 中 / 低]
理由: [判定理由を2-3文で]`;

  const payload = {
    contents: [{ parts: [{ text: prompt }] }],
    generationConfig: { temperature: 0.1 }  // 判定タスクは低temperatureで
  };

  const options = {
    method: "post",
    contentType: "application/json",
    payload: JSON.stringify(payload),
    muteHttpExceptions: true
  };

  const response = UrlFetchApp.fetch(endpoint, options);
  return JSON.parse(response.getContentText());
}
バッチ処理の現実: NotebookLMには1回の入力に約2,000行の制限がある（トークンリミットに起因）。3万行のCSVを処理するには15回以上の手動分割投入が必要。Gemini APIであれば、GASから1行ずつ（またはバッチで）自動投入でき、結果をスプレッドシートに自動書き戻しできる。ここが「NotebookLMの先」の最大の実務メリット。

各レバーの詳細

プロンプトエンジニアリング（Phase 1から即実行可能）

最もコストが低く、Phase 1でも効果が出るレバー。以下のテクニックを組み合わせる。

Few-shot prompting: 正解例を2〜3件プロンプトに含める。

以下の例を参考に、資産が「家屋の一部」か「償却資産」かを判定してください。

【例1】
資産: 受変電設備（キュービクル）
判定: 償却資産

資産: エレベーター（乗用・定員11名）

Chain-of-Thought: 判定過程を段階的に出力させる。

以下のステップに従って判定してください:

Step 1: この資産は減価償却資産か？（Yes/No）
Step 2: 自動車税・軽自動車税の対象か？（Yes → 償却資産対象外）
Step 3: 建物に附属する設備か？
  → Yes の場合: 評価要領の家屋/償却資産区分表に照らして判定
  → No の場合: 構築物・機械装置等のカテゴリを特定
Step 4: 最終判定と根拠条文を出力

ハイブリッド検索（Phase 2以降）

ベクトル検索（セマンティック）とキーワード検索（BM25等）を組み合わせる。税務文書では条文番号（「第3章第1節」）や固有名詞（「家屋疑義」）の完全一致が重要であり、ベクトル検索だけではこれらを取りこぼすことがある。

検索方式 得意 苦手
ベクトル検索 意味的に類似した文書の発見。「建物の付帯設備」→「建物附属設備」のような同義語 条文番号・固有名詞の正確なマッチ。「第3条の2」と「第3条」の区別
キーワード検索（BM25） 完全一致。条文番号、法律名の正確な検索 同義語・言い換え。ユーザーが使う表現と文書の表現のギャップ
ハイブリッド 両方の長所を統合。Reciprocal Rank Fusion（RRF）等で統合スコアを算出 重み付けのチューニングが必要

リランキング（Phase 2以降）

初回検索（Bi-encoder）で取得したTop-K候補を、より高精度なCross-encoderモデルで再スコアリングする。Bi-encoderはクエリと文書を独立にエンベディングするため高速だが精度に限界がある。Cross-encoderはクエリと文書を連結して処理するため遅いが精度が高い。

Google Cloud環境では Vertex AI Search が内部でリランキングを行っており、明示的に設定不要。自前構築の場合は cross-encoder/ms-marco-MiniLM-L-12-v2 等のオープンソースモデルを使う。

メタデータフィルタリング（Phase 2以降）

チャンクにメタデータを付与し、検索時に事前フィルタリングする。

メタデータ 値の例 用途
doc_type 評価要領 / 通達 / QA集 / 判例 根拠の優先度を制御。評価要領 > 通達 > QA
chapter 3（課税客体）, 5（課税標準） 家屋疑義なら第3章に限定して検索ノイズを削減
fiscal_year R6, R5 年度改正で変更された条文を最新版に限定
asset_category 建物附属設備 / 構築物 / 機械装置 資産カテゴリが既知の場合、関連チャンクに絞り込み

08 評価メトリクス

RAGシステムの精度を定量的に評価するためのメトリクスを定義する。「なんとなく良さそう」ではなく、数値で改善を追跡できる体制が不可欠。

Retrieval（検索）の評価

メトリクス 定義 本案件での意味 目標値
Recall@K 正解チャンクのうち、Top-K件以内に含まれた割合 家屋疑義判定に必要な条文が、検索結果K件以内に入っているか Recall@10 ≥ 0.85
Precision@K Top-K件のうち、正解チャンクの割合 検索結果に無関係な条文がどれだけ混入しているか Precision@10 ≥ 0.50
MRR 最初の正解チャンクの順位の逆数の平均 正しい条文が検索結果の何番目に出てくるか。1位なら1.0、2位なら0.5 MRR ≥ 0.70

Generation（生成）の評価

メトリクス 定義 本案件での意味 目標値
Faithfulness 生成された回答が、検索されたコンテキストに基づいているか（ハルシネーション率の逆） LLMが評価要領にない根拠を捏造していないか。税務判定で最も重要 ≥ 0.90
Answer Relevancy 回答がクエリ（質問）に対して適切か 「この資産は家屋か償却か」に対して、関係ない条文の解説をしていないか ≥ 0.85
Context Relevancy 検索されたコンテキストがクエリに対して適切か LLMに渡されたチャンクが本当に判定に必要な情報を含んでいるか ≥ 0.75

税務ドメイン固有メトリクス

汎用メトリクスに加え、償却資産税の業務目的に直結するメトリクスを設定する。

メトリクス 定義 計算方法 目標値
家屋疑義検出率（Recall） 実際の家屋疑義資産のうち、システムが正しく検出した割合 TP / (TP + FN) ≥ 0.90（見逃しを最小化）
偽陽性率（FPR） 家屋疑義でない資産を家屋疑義と誤判定した割合 FP / (FP + TN) ≤ 0.15
見逃し率（Miss Rate） 家屋疑義資産を見逃した割合 FN / (TP + FN) = 1 - Recall ≤ 0.10（税務上、見逃しは過少課税につながる）
根拠一致率 システムが挙げた根拠条文が、人間の専門家と一致した割合 一致件数 / 全判定件数 ≥ 0.80
非対称なコスト構造: 税務判定では偽陽性（不要なフラグ立て）と偽陰性（見逃し）のコストが非対称。偽陽性は人間レビューで棄却すればよいが、偽陰性は過少課税（徴収漏れ）に直結する。したがってRecallを優先的に高め、Precisionは人間レビューで補完する設計が正しい。
