# タスクマネージャー

sandbox内の複数プロジェクトを統合管理するハブ。蔵書管理（library/）、情報収集パイプライン、スキル・エージェント群を集約。

## プロジェクト構造

### .claude/ ディレクトリの配置ルール
- スキル・エージェント・コマンドは **プロジェクトルートの `.claude/`** に配置すること
- サブディレクトリ（例: `library/.claude/`）に置いても Claude Code は認識しない
- サブプロジェクト統合時は、スキル/エージェント/コマンドをルートの `.claude/` に移動し、コンテンツ資産のみサブディレクトリに配置する

## ワークフロー

### ダイジェスト生成ルール
- ダイジェストは「件数」「ランキング」ではなく、**読み物として統合**する。「この1本を読めば全部わかる」記事が目標
- 数字ベースの要約（トップ5、件数カウント）を提案しない。記事群をストーリーとして統合し、文脈の中で個別記事を紹介する
- 毎日出てくるトピックは「継続トレンド更新」セクションで**差分のみ**記述する（初出時のみフル解説）

### リモートトリガー運用上の注意
- リモートトリガーはGitHubリポジトリのクローンで動作する。ローカル生成ファイルは **git pushしない限りリモート側に存在しない**。手動実行前に必ずpush
- Anthropicのegressプロキシにより、ホワイトリスト外ドメインへのアクセス不可（403 host_not_allowed、2026-03時点。「Network access: Full」設定は効かない既知バグ）。外部API呼び出しはVPS等で実行し結果をgit pushする構成にする
- 障害診断の順序: ①`claude schedule list` で最終実行状態 → ②git_repositoryエラーならリポジトリサイズ（`git count-objects -vH`、バイナリ混入疑い）→ ③MCP接続エラーなら認証情報 → ④VPS側cronなら syslog + `.env` 構文チェック

### VPS/リモートサーバー操作の原則
- SSH経由の操作は**1コマンドずつ順次実行**。バックグラウンドで複数SSH接続を同時に張らない（VPS過負荷→応答不能の実績あり）
- SSH接続が3回連続失敗したら、追加接続せず原因調査に切り替える
- 障害時の初動: ①SSH接続確認（ダメならConoHaコンパネ再起動）→ ②`tasklist /FI "IMAGENAME eq terminal64.exe"`（MT5）→ ③同 python.exe → ④ログ末尾 → ⑤MT5未インストールならRDPでGUIインストール（SSH不可）

### 蔵書（library/articles/）の大量読み込み
- Pythonスクリプトで1件ずつ処理せず、サブエージェント並列（上限2）で直接Readする。記事は要約済みなので直読みで十分

### 製品レビュー系タスクの標準エージェント構成
単一HTML/小規模ツールの包括レビュー依頼時は4軸構成をデフォルトとする:
A. UI/UXレビュー（マイクロコピーbefore→after含む）/ B. コード品質&Why深堀り / C. 競合調査（輸入候補+アンチパターン）/ D. アーキテクチャ（分離・永続化・テスト）。
出力先は対象プロジェクトの `docs/` 配下、最後に `PLAN.md` で統合。並列上限2のため2バッチ実行（A+B → C+D）

### サブプロジェクト統合手順
1. コンテンツ資産の移動（library/, docs/ 等）
2. スキル・エージェント・コマンドを `.claude/` 配下に集約
3. settings.local.json のマージ（重複キー注意）
4. CLAUDE.md の統合（セクション追加、重複排除）
5. 全ファイルのパス参照を更新 → Grep で旧パス残存ゼロを確認
6. .gitignore の統合
7. 旧ディレクトリに跡地案内を設置

## アーキテクチャ判断

### Slack Webhook投稿
- curl + JSON直書きで日本語を送るとシェルのエスケープで壊れる。**JSONファイルを作成してから `--data @ファイル` で送る**こと

### feature-dev パターン（commands/agents 分離）への移行基準
以下のいずれかに該当したら検討する:
- 他のユーザーに配布・共有する必要が生じた
- ワークフローが5本以上に増えた
- エージェントが互いの領域を侵食し始めた

現時点では不要（ワークフロー3本、利用者1名）
