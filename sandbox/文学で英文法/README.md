# 文学で英文法 — 大学受験用ドリル

日本の中高国語で読む文学作品の場面を題材に、大学受験レベルの英文法を反復学習する単一HTMLアプリ。

- 本体: `bungakueibunpo.html`（外部ライブラリなし。フォントのみ Google Fonts）
- 収録: **8作品 / 96問** ＋ **土台トラック 159問** ＋ **診断12問**

---

## 1. 主訴 / なぜ作っているか

高校生（高2）が「自動詞・他動詞の使い分けが分からない」と言ったのが出発点。原因を切り分けた結果、以下の見立てで設計している。

- **文法用語での説明が入らない** → 用語ではなく「動詞のうしろに名詞が直結するか／前置詞というつなぎが要るか」という**型（かた）**で判定させる
- **訳語で判断すると必ず事故る** → 「〜を」だから他動詞、という推論は捨てさせる（reach the station、graduate from college）
- **理屈で覚えるより、違和感で切れる状態が本番で効く** → 例文の音読と誤文への反復接触を中心に据える
- **知らない題材の例文は頭に入らない** → 例文をすべて既読の文学作品の場面にしたところ、食いつきが明確に変わった。これが本アプリの核となる差別化点

つまり本質は文法問題集ではなく、**「知っている物語」を検索キーにして英文の型を想起させる装置**。

### 1.1 追加の見立て — 「雰囲気で読める」ことが逆に壁になっている

対象者は英会話の経験があり、**内容語（名詞・動詞）を拾って意味を復元する読み方が完成している**。会話では正しい戦略だが、この読み方は前置詞・関係詞・接続詞・語順といった機能語の情報を、意味が取れた時点で捨てている。受験英語はまさにその捨てた部分を問う。

したがって「文法が苦手」なのではなく、**文法情報を使わずに済ませる読み方が完成してしまっている**。矯正ではなく、**もう一つの読み方（骨を見る読み方）を増設する**設計にしている。

「SV が分からない」の実体は、ほぼ **主節の V を特定できない**こと。原因は3つ。

1. `-ing` / `p.p.` / `to do` が動詞に見える（準動詞と定動詞の区別がない）
2. 主語のかたまりが長いと、どこで切れるか分からない
3. `had been washed` / `did not understand` を1つの V として掴めない

これが下線部和訳・内容一致・整序・正誤のすべてで効いてくる。**診断セット**と**土台トラック**はこの一点を対象にしている。

- 1回あたり10問・数分で終わる粒度を想定

## 3. 確定している設計判断（変更するなら理由が要る）

| 判断 | 理由 |
|---|---|
| **単一HTMLファイル** | LINEやAirDropで1ファイル渡せる。オフラインで動く。ビルド不要 |
| **データとUIを分離** | 全問を `DATA` / `BONE` / `PAIRS` / `DIAG` にメタデータ付きで保持。追加はデータ行の追加だけで済ませる |
| **`localStorage` で学習記録を保存** | 「間違えた問題を次回多く出す」を成立させるため。**必ず try/catch でくるみ、失敗時はメモリ上のフォールバックに落とす** |
| **1作品＝文法項目を混ぜて完結** | 自動詞・他動詞だけでは1作品で弾切れする。作品単位で解き切れるほうが達成感が出る |
| **解説は3段構造** | 急ぐ日と復習の日で読む量を変えられるようにする |
| **外部ライブラリなし** | フォントのみGoogle Fonts。JSはバニラ |
| **作品選定は「既読で、強く覚えている作品」** | 旧版は「中高国語の定番教材」に限っていたが、検索キーとして強いのは**本人が好きな作品**のほう。定番教材と大きく重なるが、名人伝・桜の樹の下には等も候補に入る |
| **2段階解答（答え → なぜ）** | 選択肢を作り直さずに、まぐれ正解を潰す。同時に「雰囲気読みの可視化装置」として働く |

## 4. データ構造

### 4.1 文法問題（`DATA`）

```js
{
  id:     "RG1",          // 作品コード + 連番。localStorage のキーになるので変更禁止
  work:   "RG",           // WORKS のキー
  tag:    "自他動詞",      // 文法項目。結果画面の弱点集計と WHY の引き当てに使う
  format: "fill",         // "fill"=空欄補充 / "error"=誤り箇所の指摘
  kind:   "vt",           // "vt"/"vi"。空欄が埋まったときの色分けに使用（fillのみ）
  wa:     0,              // WHY[tag] の中で「正しい理由」のインデックス（2段階解答用）
  jp:     "…",            // 場面の日本語
  pre:    "They discussed",     // 空欄の前（fillのみ）
  post:   "poetry until dawn.", // 空欄の後（fillのみ）
  opts:   ["about","—（そのまま）"], // 選択肢（fillのみ）
  parts:  ["…","…","…","…"],  // 4分割された英文（errorのみ）
  ans:    1,              // 正解のインデックス
  ex:     "…",            // ① 一行の判定
  pat:    "…",            // ② 型（HTML可。<em>で正しい形、<s>で誤形）
  more:   "…",            // ③ もっと詳しく（2〜4文）
  fix:    "…"             // 正しい英文（errorのみ）
}
```

**`id` は学習記録のキー**なので、既存問題のidを振り直すと記録が壊れる。問題を差し替えるときは新しいidを振る。

### 4.2 理由の選択肢（`WHY`）

文法項目（`tag`）ごとに 3〜4 個の「理由」を持ち、各問の `wa` が正解を指す。表示時にシャッフルされる。

- **同じ tag の中でつねに同じ理由が正解になる項目がある**（時制・知覚動詞など）。これは意図的で、狙いは「答えを当てる」ことではなく「規則を言葉にできる」ことだから。選択肢はシャッフルされるので位置で覚えることはできない。
- 新しい文法項目を足すときは、`WHY` にセットを追加してから `tag` を使うこと（起動時の検証はないが、`wa` が範囲外だと理由が出ない）。

### 4.3 骨（`BONE`） — 土台トラックの土台

```js
{
  id:"B01", w:"RG",            // 作品コード
  toks:["Hearing","his",...],  // 単語（句読点込み）
  s:[4,5],                     // 主語のトークン番号
  v:[6],                       // 主節の動詞のトークン番号（複数語なら複数）
  p:"SVO",                     // 文型
  trap:[0],                    // 動詞と間違えやすいトークン（今は記録用。将来の分析に使う）
  role:{f:0,t:3,a:2},          // 任意。かたまり f..t の働き 0=名詞 1=形容詞 2=副詞
  note:"…"                     // 解説
}
```

**例文はすべて `DATA` と同じ文**。同じ文を「文法項目として」「骨として」2回見せることで想起を強化する狙い。

### 4.4 ペア（`PAIRS`） / 診断（`DIAG`）

- `PAIRS` … 訳がほぼ同じで文型が違う2文。`ask` に指定した文型を持つのは必ず片方だけ
- `DIAG` … `BONE` の id を参照。`m[0]` が正しい和訳（表示時にシャッフル）

## 5. 実装済みの機能

**診断（初回導線）**
- 既読3作品の6文について「意味」と「構造」を続けて聞く（12問）
- 結果を **意味 n/6 ／ 構造 n/6** の2本のバーで表示。差が2以上なら「意味は取れている。取れていないのは骨」と言い切る
- 結果は保存され、ホームに常時表示。何度でもやり直せる（Lv一周後の再診断が一番のご褒美になる想定）

**土台トラック（作品縛りなし・例文は既存文の使い回し）**

| Lv | 内容 | 問数 |
|---|---|---|
| Lv0 | かたまりの、はたらき（名詞／形容詞／副詞） | 18 |
| Lv1 | 動詞さがし（主節の V をタップ） | 43 |
| Lv2 | 主語さがし（V を示したうえで S をタップ） | 43 |
| Lv3 | 文型を決める（SV / SVO / SVC / SVOO / SVOC） | 43 |
| Lv4 | 意味は同じ、構造がちがう（対比ペア） | 12 |

Lv3 の判定手順は既存の「型」思想の直系：
① V のうしろに名詞があるか → ない = SV ／ ② その名詞は S とイコールか → イコール = SVC、別物 = SVO ／ ③ 名詞が2つ並ぶ → 2つがイコール = SVOC、別物 = SVOO

**作品から解く**
- 作品別カード8枚（問題数・正答率）、全作品ミックス、苦手な問題だけ
- `weight()` による重み付き抽選（未挑戦を優先、誤答回数が多いほど高確率）。1セット10問
- **同じ文法項目が連続しないよう並べ直す**（残数の多い項目から出す貪欲法。理論上の最小まで下がる）
- 出題形式2種：空欄補充／誤り箇所の指摘

**2段階解答**
- 答えを選ぶ → **正誤を見せずに**「なぜ？」を3〜4択で聞く → まとめて開示
- 答え○・理由× は「惜しい」と表示し、**記録上は誤答**にする
- ホームのチェックでオフにできる（急ぐ日用）。既定はオン

**解答後 / 結果**
- 正誤 → 一行の判定 → 型 → 「もっと詳しく」（開閉式）
- スコア、文法項目別の取りこぼし集計、間違えた問題だけ再挑戦、学習記録のリセット

## 6. コンテンツ作成のルール（追加時はここに従う）

**作品選定**
- **本人が既読で、あらすじと場面を強く覚えている作品**を最優先。中高国語の定番教材とはおおむね重なる
- 現在収録：山月記／檸檬／蜜柑／羅生門／走れメロス／少年の日の思い出／高瀬舟／夢十夜
- 追加候補：名人伝、桜の樹の下には、トロッコ、鼻、こころ、城の崎にて、故郷、女生徒

**場面選び**
- あらすじを思い出せる**象徴的な場面**だけを使う。細部やマイナーな箇所は使わない
- 1作品12問。同一場面から2問作って対比させるのは有効（例：檸檬の lie / lay、夢十夜の rise / raise、高瀬舟の watch / stare）

**英文**
- 受験標準レベル。1文につき論点は1つだけ
- 固有名詞はローマ字表記（Melos, Yuan Can, Kisuke）。訳しにくい語は避ける
- 場面の解釈が原作と食い違わないこと
- **和文が誤答側の英文としても成立しないこと**。旧版の LM1 は和文が「置かれていた」だったため `was laid` も正しくなってしまい、出題として破綻していた（修正済み）

**選択肢**
- 誤答は「実際にやりがちなミス」であること
- `—（そのまま）` は直結を表す固定表記

**解説（3段）**
1. `ex` … なぜその答えになるかを一行で
2. `pat` … パターンだけを抜き出す。誤形は `<s>` で見せる
3. `more` … 関連知識・入試での狙われ方。**他の作品の問題への橋渡しを入れる**（例：檸檬の lie/lay → 夢十夜の rise/raise）

**文法項目の配分**
1作品につき、自他動詞3〜4問＋その他の頻出項目を混ぜる。現在の `tag` 一覧（20種）：
自他動詞／知覚動詞／使役動詞／分詞／分詞構文／時制／関係詞／仮定法／動名詞／不定詞／比較／接続詞／前置詞／進行形／熟語／助動詞／受動態／強調構文／倒置／同格

## 7. 今後の拡張（優先順）

1. **正誤問題を各作品3〜4問に増やす** — 入試の主要形式。現状は各1問（全96問中8問）にとどまる
2. **整序問題（並べ替え）の追加** — `format:"order"` を新設。文型の理解確認としては最強。Lv3 の次に置く
3. **「会話ならOK、入試ならNG」枠** — `It's me.` / `Who did you talk to?` / `less people` など、直感が減点される理由を明示する。対象者の背景に直撃するので効果が見込める
4. **修飾の畳み込み** — 長文の修飾を `( )` で括らせる。下線部和訳の実作業そのもの。Lv5 相当
5. **作品の追加** — 名人伝・桜の樹の下には・トロッコが有力
6. **読み上げ（Web Speech API）** — 外部ライブラリ不要。**正文だけ**読み上げる（誤形は音にしない）
7. **和文英訳モード** — 日本語だけ見て英文を口頭再現、自己採点式
8. **復習間隔の調整** — 現在は誤答回数のみの重み付け。最終解答日を見た間隔反復（`s.t` は保存済みで未使用）
9. **一覧／辞書ビュー** — 全問を項目別に通読できる画面

## 8. 注意点

- `localStorage` は必ず try/catch。キーは2つ（`bungaku-eibunpo.v1` = 問題ごとの正誤 / `bungaku-eibunpo.meta.v1` = 設定と診断結果）。**前者は旧版と互換なので、旧版の記録はそのまま引き継がれる**
- **`file://` で開くと `localStorage` が使えない環境がある**（記録が毎回消える）。落ちはしないが気づきにくい。記録の信頼性を上げたいなら GitHub Pages 等に置いて URL で配布するほうがよい
- 問題の追加時は `id` の重複に注意
- `pat` と `more` は `innerHTML` で描画している。データはこちらで書くので現状問題ないが、外部入力を混ぜる設計にはしないこと
- `weight()` は **0以下に落とさない**（クランプを外すと、習熟した問題の抽選順が固定化して毎回同じ順で出る）
- 英文は inline フローで描画している（flex + gap をやめた）。`post` が句読点で始まる場合に空白を入れない処理が入っている
- スマホ縦画面が主戦場。1問が1〜2スクロールに収まるかを毎回確認する

## 9. 検証

データ整合性とUIの通し確認は、`node --check` ＋ Playwright（Chromium）で実施している。確認済みの範囲：

- `DATA` 96問すべてで、描画・採点・3段解説・空欄の色分けが成立すること
- 土台トラック 159問すべてで、正解判定と解説が成立すること
- `id` 重複なし、`ans` / `wa` / `BONE` のトークン番号がすべて範囲内
- `PAIRS` の `ask` が必ず片方だけに一致すること
- 診断12問の通し → 2本のバー表示 → 保存 → ホーム反映
- 2段階解答で「答え○・理由×」が誤答として記録されること
- 同一項目の隣接が 0 件（山月記セット200回・1800隣接箇所）
- 全問正答済みでも `weight > 0` で、先頭に来る問題が固定されないこと
- リロード後の記録の持ち越しと、リセット
